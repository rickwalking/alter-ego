### Summary
P1 of the carousel generation queue (ADR-0026): carousel generation leaves the web process and runs in a
resource-capped PgQueuer worker.

- **Record and outbox.** `generation_runs` (Alembic `d1b0cf9cd80d` + the deploy one-shot
  `python -m rag_backend.scripts.generation_queue_schema --apply --verify`, DDL compiled from the ORM table) is the
  queue's source of truth. The dashboard resume stages its run in the same transaction as the lock bump and the
  `in_progress` flip (the web never runs the phase). Autopilot approvals are already durable compare-and-sets on
  `autopilot_runs`; the dispatcher stages one run per active autopilot run within 10 s.
- **Dispatcher (worker, every 10 s).** Stages missing autopilot runs, hands queued rows to PgQueuer (job looked up by
  dedupe key first), re-queues rows whose job vanished, and mirrors held (`failed`) jobs to `dead_letter` with one
  owner notice, then drops the held job.
- **Worker** (`rag_backend.worker.main:create_pgqueuer`, `pgq run … --heartbeat-timeout 300 --batch-size 1`): one
  entrypoint `carousel_generation` with `concurrency_limit = GENERATION_WORKER_CONCURRENCY` (1) and
  `on_failure="hold"`, so FIFO and the limit hold across kinds. Refuses to start unless the checkpointer is
  `postgres`. Runs the heavy periodic steps moved off the web loop (stale-run reaper, drift reconciler, republish
  sweeper, autopilot sweep). Engine without `create_all`, its own small pool, a long-lived connection named
  `generation-worker`.
- **Executors.** `autopilot_drive` steps one run until it waits for the owner or ends (WAIT → retried in 60 s keeping
  its FIFO position; SIGTERM → stops at the next phase boundary and is retried at once). `workflow_resume` runs the
  dashboard decision once.
- **Budgets and failures.** Our own counters: ≤ 3 unfinished starts per (run, phase), ≤ 10 per run; a phase that
  finishes takes its start back, so an advancing run is never poison. Transient errors (timeouts, dropped
  connections, provider outages/rate limits) retry 30 s × 2ⁿ up to 30 min with ±20 % jitter; permanent errors
  (validation, bad payload, `MemoryError`) and exhausted budgets dead-letter at once. An autopilot dead letter parks
  the run as `escalated` / `failed` with `queue_dead_letter:<code>` (one Telegram notice through the outbox); a
  dashboard dead letter marks the project `failed` and publishes the run's end.
- **Ownership.** A per-project drive lock (session advisory locks, own key space, dedicated AUTOCOMMIT connection,
  watchdog that aborts the drive when the connection dies) is the only ownership primitive; the synchronous dashboard
  start takes it too (409 `mutation_in_progress` while the worker drives). A job that gets the lock and finds its
  project `in_progress` reaps it at once and re-drives the parked node: a run interrupted by a deploy or a crash
  resumes instead of escalating `run_stale`. A re-picked dashboard resume never re-sends the review decision.
- **Side effects re-delivery can hit** (AE-0520 inventory): a re-delivered start reuses the run's carousel (id derived
  from the run); a re-run image waits on the Grok Bot job still pending for the same image and prompt.
- **Progress relay.** The worker installs a hub that also sends each SSE event as `NOTIFY carousel_progress`; the web
  listens and republishes into its own hub (oversized review events are rebuilt from the checkpoint); run-stage
  mirroring follows the events.
- **Health and alerts.** `/health/ready` gets a `generation_queue` entry (depth, retry_wait, dead letters, oldest
  queued and running ages, worker connected). The web alerts Pedro through the alerts bot once per episode when the
  worker is gone 10 min or the oldest queued run waits over 6 h.
- **Deploy.** The one-shot runs after the archived_at step (never blocks the stack, fails the job at the end); the
  worker is drained (`stop -t 300 generation-worker`) before `down`.
- **Compose.** `generation-worker`: same image, `mem_limit` = `memswap_limit` = 1344m, `cpus` 1.0, `cpu_shares` 256,
  `shm_size` 256m, `pids_limit` 512, read-only root + tmpfs, `cap_drop: ALL`, `no-new-privileges`, no ports, own
  healthcheck (dispatcher liveness file), `stop_grace_period` 300s; only the env vars the worker needs (no web-only
  secrets; placeholder `SECRET_KEY`, it signs no tokens). Chromium runs with Playwright's default `--no-sandbox` under
  those controls. The dev stack runs the worker too, both on the Postgres checkpointer.
- **Rollback.** Revert, preceded by the drain and `python -m rag_backend.scripts.generation_queue_rollback --apply`
  (puts unstarted dashboard resumes back at their gate, cancels active runs); plan §7.
- **Validation tooling** (`ops/queue-validation/`): droplet provisioning through the DigitalOcean API (token file
  outside the repo), stubbed `.env` + credential-hash check, egress closed after the build, mock upstream (LLM, Grok
  image webhook, sources), synthetic seed, load p95 verdict, worker kill and full deploy mid-run, duplicate checks,
  teardown on any exit.

holds. (b) delayed enqueue — holds. (c) configurable heartbeat timeout re-picks a stale job — holds. (d) a stale
re-pick counts no attempt — confirmed, so our counter is required. (e) FIFO under `concurrency_limit=1` — holds.
(f) held-job requeue resets attempts — holds. (g) a schedule is claimed once across workers — holds. (h) PgQueuer has
no age-based purge API; deleting `pgqueuer_log` rows by `created` works and aggregation still runs — AE-0524 must
purge itself.
