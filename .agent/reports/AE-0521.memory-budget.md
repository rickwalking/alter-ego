With Langfuse capped at 768 MiB that instant would have been 2286 − (993 − 768) = 2061 MiB (an earlier version of
this report said 2087). Without the Langfuse stack (web, worker, ClickHouse, MinIO), the maximum over the same window
is 800 MiB. Postgres: at most 13 client connections.

Sizing rule: measured peak + 30 %, rounded up, with these exceptions:
- frontend: 384M rather than 256M: Next.js image optimization encodes AVIF for remote images, which the quiet
  sampling window probably never exercised.
- backend: the prod run peak (1222 MiB) + 30 % = 1589 → 1600M. The reservation (384M) covers the web peak.
- redis: 128M rather than 64M: Redis has no `maxmemory`, serves the backend and forks for AOF rewrites
  (copy-on-write), so a cgroup kill would drop its data in flight; the peak is 15 MiB.
- postgres: 384M covers `shared_buffers` (128 MB) plus work memory for both databases; the cgroup also charges
  page cache, which it reclaims before killing.
- Langfuse: the 768M cap with a 448 MiB Node heap crash-looped Langfuse web on prod after the deploy (1,050
  restarts, `JavaScript heap out of memory`; RSS peak 1105 MiB). Pedro moved tracing to Langfuse Cloud (Hobby tier):
  Langfuse web, Langfuse worker, ClickHouse and MinIO are off the droplet (AE-0545).

## Deploys

Deploys build and pull on the box and exhausted swap again at 02:36 UTC (2047/2047 MiB, 112 MiB available). The caps
do not change that; keep deploys out of the generation window until images are built off the box.

## Rollback per cap

Remove that service's `deploy.resources` block (or set the old value) and deploy. A container killed by its cap
shows `OOMKilled: true` in `docker inspect` and restarts on its own (`restart: unless-stopped`).
