With Langfuse capped at 768 MiB the same instant is ≈ 2087 MiB. Postgres: at most 13 client connections.

Sizing rule: measured peak + 30 %, rounded up, with these exceptions:
- frontend: 384M rather than 256M: Next.js image optimization encodes AVIF for remote images, which the quiet
  sampling window probably never exercised.
- backend: the run peak above (1011 MiB) + 30 % = 1314 → 1344M. The reservation (384M) covers the web peak.
- redis: 128M rather than 64M: Redis has no `maxmemory`, carries Langfuse's queues and forks for AOF rewrites
  (copy-on-write), so a cgroup kill would drop the queue; the peak is 15 MiB.
- postgres: 384M covers `shared_buffers` (128 MB) plus work memory for both databases; the cgroup also charges
  page cache, which it reclaims before killing.
- Langfuse web: observed 993 MiB uncapped, so the Node heap limit (448 MiB, leaving ≥ 256 MiB for native memory)
  is what keeps it under 768M.

P1 sizing (Pedro, 2026-10-23): the plan's earlier worker target (≤ 900 MiB) was below the measured run peak
(≈ 1011 MiB), so an HD export inside it would be OOM-killed. AE-0522 caps the worker at 1344M and lowers the backend
to its web peak + 30 % (512M) in the same change; the budget above already assumes that split. Until AE-0522 merges
the backend keeps 1344M, because it still runs the HD exports.

## Rollback per cap

Remove that service's `deploy.resources` block (or set the old value) and deploy; for ClickHouse also restore the
0.8 ratio in `clickhouse-config/low-memory.xml`, and for Langfuse drop `NODE_OPTIONS`. A container killed by its cap
shows `OOMKilled: true` in `docker inspect` and restarts on its own (`restart: unless-stopped`).
