# AE-0431 — Dev summary

Branch `feat/ae-0431-logout-redirect-internal-host` from `origin/main`. Frontend only.
Source: orchestrator-verified prod evidence (2026-10-19, right after AE-0429 #150
deployed): `GET /auth/logout` answered 307 with
`Location: https://0.0.0.0:3000/login?redirect=...&error=session_expired`.

## What changed

1. **Host-independent login URL** — `frontend/src/app/auth/logout/route.ts` no longer
   uses `request.url`'s host. A `buildLoginUrl()` derives the origin from the proxy
   headers: host from `Host` (`nginx $host`), scheme from the first
   `X-Forwarded-Proto` value (restricted to `http`/`https`), falling back to the
   request origin when a header is missing (local/dev, direct requests).
2. **Defensive host parse** — `applyForwardedHost()` parses the Host header via the
   URL API (fixing the `.host =` port-leak footgun and handling `host:port`) and
   ignores malformed values instead of throwing a 500 on logout. The bind-address
   port (`:3000`) can no longer leak into the Location.
3. **Constants** — `HTTP_HEADER_HOST`, `HTTP_HEADER_X_FORWARDED_PROTO`,
   `FORWARDED_PROTOCOLS` added to `src/constants/auth.ts`;
   `isSecureRequest` (`modules/identity/lib/auth-cookie.ts`) now reuses the
   forwarded-proto constant.
4. **Contract untouched** — `sanitizeLoginRedirect`, `error=session_expired`,
   best-effort backend POST and the cookie clearing behave exactly as before
   (existing tests unmodified and green).
5. **Grep audit** — `NextResponse.redirect(` under `frontend/src/app/**/route.ts`
   matches only the logout handler; middleware is left as is (it sees the proxied
   Host and works in prod).

## Root causes

- `route.ts:19` built `new URL('/login', request.url)`. Under the Next standalone
  server, `request.url` is the `initURL` from `attachRequestMeta`
  (`next-server.js`): with `fetchHostname` + `port` set (`server.js` binds
  `0.0.0.0:3000`), the URL is `https://0.0.0.0:3000<path>` — the bind address. The
  `https` scheme comes from `X-Forwarded-Proto`; the host does not get replaced.
- Middleware works because it receives the proxied Host (`Host $host` in
  `nginx/nginx.conf.ssl` frontend location), so `new URL('/login', request.url)`
  resolves against the public host there.
- `NextResponse.redirect` in Next 16.4 (`validateURL`) rejects relative URLs, so the
  fix must build an absolute URL from the forwarded headers.

## Decisions / deviations

- **Headers over `trustHostHeader`**: a one-route fix with the same trust model as
  the working middleware, instead of a Next config flip that changes `request.url`
  for every route/middleware/API handler (app-wide blast radius).
- **`Host` header (nginx `$host`), not `X-Forwarded-Host`**: the frontend location
  does not forward `X-Forwarded-Host`; `Host` is always set. Client-controllable,
  but the Location only ever points at the host the user already addressed — the
  same exposure middleware has today — and the `redirect` param itself stays
  path-sanitized by `sanitizeLoginRedirect`.
- **Scheme restricted to http/https**: a malformed forwarded proto cannot produce a
  non-http Location.
- **Deviation from the brief's "relative Location" option**: impossible — Next 16.4
  `NextResponse.redirect` (`validateURL`) throws on relative URLs. Absolute URL from
  forwarded headers is the brief's other sanctioned option.
