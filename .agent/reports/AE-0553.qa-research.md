## 3. Architecture & Data Flow [security, code-quality]

Runtime: PgQueuer schedule → `run_daily_scan` → `DailyRecoveryScan.run_once` → recoverable read → one bridge session per item → stale recovery → purge → counts/orphans → report → `summary_text` → existing alerts sender.

Per item:
1. `_locked_run` selects the autopilot row `FOR UPDATE`, then reads it in the same session.
2. Public `mark_recovery_attempt` locks the exact generation row, checks dead-letter status and marker, updates payload without commit.
3. Missing/resolved/already-recovered autopilot rows still commit the marker, preserving AE-0524 behavior.
4. `_revive_once` uses existing `run_revive.revive`: escalated CAS plus generation requeue, or failed-terminal replacement run; notice ledger and audit/outbox share the transaction.
5. `_revive_once` commits once. An exception before commit rolls back marker and all staged writes; the scan catches after session exit.

Owner retry writes autopilot first then generation, matching the scan lock order. Its response is deferred until after commit.

Trust boundaries: internal scheduler and DB only; no new auth/API surface. Logs exclude exception objects/messages and `exc_info`. The summary deliberately uses bounded `str(exc)` and is sent only to Pedro's configured alerts chat. No LLM/prompt execution is added.
