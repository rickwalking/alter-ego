# Architecture Plan: AE-0572 — Owner-approved Instagram boosts

**Date:** 2026-10-29
**Status:** Ready for development
**Tier:** T3 (phase 1 and phase 2 are independently shippable; phase 3 spends money)
**ADR:** [ADR-0029](../../docs/decisions/0029-owner-approved-instagram-boosts.md) (proposed). Accept it before `BOOST_ENABLED=true`. Phase 1 does not depend on acceptance.

Code inspected on this branch. Paths below are under `backend/src/rag_backend/` unless stated.

## Goal and evidence

A boost bot that already has the autopilot `X-Api-Key` can read organic performance for every post on the Instagram account, propose a boost, and have that boost spend money only after the Telegram owner taps Approve.

What the code does today:

- `GET /api/instagram/insights` is editor/admin JWT (`require_editor_or_admin`), rate-limited with `RATE_LIMIT_WORKFLOW_ENDPOINTS`, and mounted from `api/insights.py` in `bootstrap/app_factory.py`. It is not on the autopilot router.
- `SqlInsightsStore.published_posts` reads `autopilot_runs.ig_post_id` and the manual publish ledger only, newest 30 (`INSIGHTS_POST_LIMIT`). Posts created in the Instagram app are absent.
- Graph metrics requested today are exactly `views, reach, saved, shares, follows, profile_visits, total_interactions` (`insights_constants.INSIGHT_METRICS`). Likes, comments, media type, product type and timestamps are not stored. `InsightMetrics.from_values` ignores unknown names. Null means "Graph did not return it".
- Snapshots live in `instagram_post_insights` (Alembic `c2d3e4f5a6b7`). `_write` assigns every metric column from the domain object, so a writer that does not know about a new column will null it if we are careless.
- Refresh is a 6 h TTL (`is_due`) and at most 10 Graph reads per request. The gateway asks for the whole metric list, then one metric at a time on a non-transient refusal. Transient errors keep the last snapshot and set `stale`.
- The Instagram host is pinned: `GRAPH_HOST_INSTAGRAM = https://graph.instagram.com/v23.0`. `GRAPH_HOST_FACEBOOK` already exists beside it. The publisher documents IGAA tokens on `graph.instagram.com`.
- `require_autopilot_api_key` hashes `X-Api-Key` with sha256 and compares it to `GROKBOT_API_KEY_SHA256`. Missing digest is 503 `autopilot_api_key_unconfigured`. Bad key is 401 `invalid_api_key`. The dependency does not attach a user. ADR-0020 limits that key to `/api/autopilot/*`.
- Owner buttons already go through `OwnerActionService.handle`: `claim_update`, then `is_owner(actor_id, TELEGRAM_OWNER_CHAT_ID)`. Callbacks are dispatched in `_on_callback` to the thesis mixin, the cover mixin, the queue mixin, then `parse_callback`. Existing owner copy is plain text. There is no `parse_mode`.
- The worker loop interval is `workflow_worker_interval_seconds` (default 60). Publish, credential refresh and Telegram notify are steps from `bootstrap/autopilot_worker_factory.py`. Advisory locks already exist.
- Alembic's single head is `e7a91c4d2f60` (`tests/integration/test_autopilot_migration.py` `ALEMBIC_HEAD`). Revision ids `a1b2c3d4e5f6` and `b2c3d4e5f6a7` are already used. Do not edit `c2d3e4f5a6b7`.
- `modules/autopilot/api/schemas.py` is about 367 lines. New response models go in new files so the 400-line cap holds.
- `owner_actions.py` is near that cap. Boost callbacks are a mixin, same as `ThesisOwnerActions`.
- No Marketing API, ad account setting, or boost table exists. `log_redaction.py` already rewrites `access_token=` query values.
- Env names used by autopilot must appear in `.github/workflows/deploy.yml` and `docker-compose.prod.yml`. `scripts/ci/check_autopilot_env_parity.py` fails otherwise, and its rule-fires test must be updated.

## Decisions

1. Separate System User token for ads. The IGAA token stays on `graph.instagram.com` for publish and organic insights.
2. The API key creates and reads boost requests. It cannot approve, launch, pause or edit.
3. Ads objects are created `PAUSED`. Ids are stored after each step. Activation is last, and only if `BOOST_ENABLED` is still true.
4. Caps run at create, approval and launch. Pending rows count toward the weekly cap. An ad-account spend cap in Business Manager is the Meta-side backstop.
5. Version 1 objective is engagement only (`OUTCOME_ENGAGEMENT`, `POST_ENGAGEMENT`, `destination_type=ON_POST`).
6. Weekly cap window is `created_at >= now - 7 days` in UTC.
7. Product minimum daily budget defaults to 600 cents. Launch also refuses a budget under the ad account's `min_daily_budget_high_freq` (Meta's minimum-budget reference: high-frequency actions such as likes).
8. Meta's "Use Posts as Instagram Ads" guide says the media id from the Instagram media endpoints is the `source_instagram_media_id`, and that `boost_eligibility_info` reports whether it can be promoted. The page fetch timed out during planning; the launcher still preflights the id with the ads token and fails closed with `media_not_visible_to_ads` when that read fails. Re-read the guide before the first live boost.
9. Telegram boost copy is the Portuguese text in this plan (owner-specified). Other owner messages stay English.
10. `BOOST_REQUESTS_ENABLED` and `BOOST_ENABLED` default false. The parity checker treats them like `AUTOPILOT_ENABLED`: a deploy must not turn them on by omission.

## Options considered

See ADR-0029. Inside the backend, the insights read reuses `GraphInsightsGateway`, `is_due`, `guard_graph` and `instagram_post_insights` rather than a second snapshot table. The extra columns are nullable and the write set is explicit, so the dashboard response schema does not change.

## Phase 1 — `GET /api/autopilot/ig-insights` (AE-0573)

### Contract

Auth and 401/503 are the existing dependency, applied on the router the same way as `api/router.py`. Rate limit is the shared autopilot bucket: `@limiter.shared_limit(RATE_LIMIT_AUTOPILOT, RATE_LIMIT_SCOPE_AUTOPILOT)` (10/minute per IP). Response header `Cache-Control: no-store`.

| Query | Default | Rule |
| --- | --- | --- |
| `since` | now − 30 days | Inclusive lower bound on `posted_at`. Older than 90 days is 422 `since_too_old`. |
| `until` | now | Exclusive upper bound. |
| `limit` | 30 | 1–100. |
| `media_type` | all | `IMAGE`, `CAROUSEL_ALBUM`, `VIDEO`. |
| `product_type` | all | `FEED` or `REELS`. Stories are never stored. |
| `refresh` | false | When true, the 10-read budget is spent on the oldest due snapshots in the page first. It does not raise the budget. |

`configured` is false when `META_IG_USER_ID` is empty or the gateway is missing. The body is then empty items, empty baselines, `configured: false`. That is not a 503.

`list_truncated` is true when the Graph media walk hit the page cap before the `since` bound. The bot should call again later; it should not treat the page as the full account.

### Graph

Host and version: `settings.meta_ig_graph_base` (default `GRAPH_HOST_INSTAGRAM`, v23.0). Token: `token_provider_for`, the same provider as the publisher. Never log the token. Reuse `guard_graph`, `error_from`, `json_dict`.

Media list, paginated with `paging.cursors.after`, at most 4 pages of 50 per request:

`GET /{ig-user-id}/media?fields=id,caption,media_type,media_product_type,timestamp,permalink,like_count,comments_count,thumbnail_url,media_url&limit=50`

Stop when a page's oldest timestamp is before `since`, when `limit` in-range items are collected, or at the page cap. Skip `STORY`. `like_count` may be absent when likes are hidden; store null. Persist a 280-character caption excerpt (`strip_controls`), never the full caption, and do not persist `media_url` (it is a short-lived CDN URL).

Per media id, one insights call. Metric names are constants:

| `media_product_type` | Request | Do not request |
| --- | --- | --- |
| `FEED` (`IMAGE`, `CAROUSEL_ALBUM`) | `views, reach, saved, shares, likes, comments, follows, profile_visits, total_interactions` | reel watch-time metrics |
| `REELS` | `views, reach, saved, shares, likes, comments, total_interactions, ig_reels_avg_watch_time, ig_reels_video_view_total_time` | `follows`, `profile_visits` |

Never request `impressions`, `plays`, `clips_replays_count`, `ig_reels_aggregated_all_plays_count`, or `video_views`. A test lists the requested tuple and fails if a deprecated name appears. Keep the existing whole-list-then-one-by-one fallback. A refused metric stays null, never 0. HTTP 429 and error codes 4, 17, 32, 613 stay transient (`InstagramGraphError.transient`) and keep the previous snapshot.

`likes` and `comments` here are the insights metrics. `like_count` and `comments_count` are the media fields. Both are returned; they can differ, and a hidden like count is null.

Organic insights exclude paid interactions. Paid results are phase 3 ad insights only.

Required scope is `instagram_business_basic` plus `instagram_business_manage_insights`. The existing dashboard can be all nulls if the scope is missing, so a working dashboard does not prove the scope. Add `scripts/ops/ig_scope_probe.py` that reads one media id's `reach,saved` and prints `ok` or `missing_scope`. It takes the token from the environment, prints no token, and is not on the request path. Regenerate the long-lived token through the existing credential seed (`PROVIDER_INSTAGRAM`) if the probe says missing.

### Response

Pydantic models in `modules/autopilot/api/ig_insights_schemas.py` with `extra=forbid` on query models. Shape:

- `items[]` newest first: `media_id`, `media_type`, `media_product_type`, `permalink`, `caption_excerpt` (max 280), `timestamp`, `age_hours`, `carousel_project_id`, `topic`, `like_count`, `comments_count`, `metrics`, `rates`, `fetched_at`, `stale`, `boost` (null until phase 2).
- `metrics`: `views`, `reach`, `likes`, `comments`, `saved`, `shares`, `follows`, `profile_visits`, `total_interactions`, `avg_watch_time_ms`, `total_watch_time_ms`. Integers or null. Reel-only and feed-only fields are null on the other type.
- `rates`, null when a numerator is null or a denominator is null or 0: `shares_per_100_views` (reuse `shares_per_100`, 2 decimals), `saves_per_100_reach` (2 decimals), `follows_per_1000_reach` (2 decimals), `engagement_rate` = `total_interactions / reach` (4 decimals).
- `baseline`: keys `FEED` and `REELS`. Each has `sample_size`, `median_reach`, `median_shares_per_100_views`, `median_saves_per_100_reach`, `median_follows_per_1000_reach`, `median_engagement_rate`. A median is null when no row has that rate. `sample_size` is the number of posts in the window, including ones with null rates. The API still returns a baseline when `sample_size` is under 5; the bot is the one that skips scoring.
- `next_until`: `posted_at` of the oldest item when the page is full, else null.
- `configured`, `list_truncated`, `generated_at`.

`carousel_project_id` and `topic` come from the same two sources as `SqlInsightsStore` (`autopilot_runs` and the manual ledger joined to `carousel_projects.topic` through a table clause, not the carousel ORM). Unmatched media leaves both null.

`boost` stays null in phase 1. Phase 2 fills the latest non-terminal request (`request_id`, `status`) without an extra client call.

### Bot scoring (no other calls)

Every 6 hours the bot calls `GET /api/autopilot/ig-insights?since=<now-7d>&limit=50`.

Candidates: `age_hours` in `[24, 72]`, `stale=false`, `boost=null`, product type `FEED` or `REELS`.

If `baseline[product_type].sample_size` is under 5, skip that type. Otherwise:

- `r_share = shares_per_100_views / median` weight 0.35
- `r_save = saves_per_100_reach / median` weight 0.30
- `r_follow = follows_per_1000_reach / median` weight 0.20
- `r_eng = engagement_rate / median` weight 0.15

A null ratio contributes nothing and its weight is dropped (renormalize). Reels have no follow rate; their follow weight moves to share and save in proportion (0.35 and 0.30 become 0.4375 and 0.375, engagement stays 0.15). `score = sum(weight * min(r, 3))`. Require `reach >= 0.5 * median_reach` and `score >= 1.4`. At most one proposal per day. This scoring is bot-side. The backend stores the bot's `score` for audit and does not recompute it.

## Phase 2 — boost requests and Telegram approval (AE-0574)

Depends on phase 1 (`ig_media` must contain the post).

### Routes

All under `/api/autopilot`, API key, shared 10/minute bucket except the create route.

| Method | Path | Limit | Effect |
| --- | --- | --- | --- |
| `POST` | `/boost-request` | shared bucket plus `RATE_LIMIT_AUTOPILOT_BOOST = 5/hour` per IP, same pattern as `RATE_LIMIT_AUTOPILOT_ASSETS` | insert `pending_approval`, then Telegram |
| `GET` | `/boost-request/{id}` | shared | row, Meta ids, last ad insights from Postgres only |
| `GET` | `/boost-requests` | shared | newest first. Repeatable `status`, optional `media_id`, `limit` default 20 max 100 |

No route approves, launches, edits or stops. Error `detail` is a stable string, matching `HTTPException(detail=code)` in `api/auth.py`. Pydantic body errors stay FastAPI's 422 validation body.

`Idempotency-Key` header is required, 8–128 chars `[A-Za-z0-9_-]`. The row stores `sha256` of the canonical JSON body (sorted keys, no whitespace). Same key and same hash return the stored row with 200. Same key and a different hash return 409 `idempotency_key_reused`. A new key returns 202.

### Body

`extra=forbid`.

- `media_id`: `^[0-9]{5,32}$`
- `daily_budget_cents`: int `> 0`, minor units of the account currency (centavos when the account is BRL)
- `days`: int `>= 1`
- `objective`: only `engagement` in v1. Any other value, including `awareness`, is 422 `objective_not_supported`
- `audience`: `countries` default `["BR"]`, `age_min` default 18, `age_max` default 65. No interests or custom audiences.
- `reason`: 10–600 chars after `strip_controls`, shown verbatim in Telegram
- `score`: optional float, stored, not used for policy
- `start_at`: optional, default is approval time

`total_budget_cents = daily_budget_cents * days`. `currency` is the setting `BOOST_CURRENCY` (default `BRL`) until phase 3 reads the ad account. If the account currency differs, launch fails with `currency_mismatch` before any create call.

### Policy (`domain/boost_policy.py`)

Pure. The same function runs at create, at approval and at launch. Nothing is written when create fails.

| Rule | Setting | Default | Error |
| --- | --- | --- | --- |
| Feature on | `BOOST_REQUESTS_ENABLED` | false | 503 `boost_disabled` |
| Daily budget ≤ | `BOOST_MAX_DAILY_BUDGET_CENTS` | 3000 | 422 `daily_budget_over_cap` |
| Daily budget ≥ | `BOOST_MIN_DAILY_BUDGET_CENTS` | 600 | 422 `daily_budget_under_floor` |
| Days ≤ | `BOOST_MAX_DAYS` | 7 | 422 `days_over_cap` |
| Committed cents in rolling 7 days + this request ≤ | `BOOST_MAX_TOTAL_CENTS_PER_WEEK` | 10000 | 422 `weekly_cap_exceeded` |
| One non-terminal row per `media_id` | partial unique index | | 409 `boost_already_active` |
| Pending count < | `BOOST_MAX_PENDING` | 3 | 429 `too_many_pending` |
| Row in `ig_media`, product type `FEED` or `REELS`, age ≤ | `BOOST_MAX_MEDIA_AGE_DAYS` | 30 | 422 `media_not_eligible` |
| Countries subset of | `BOOST_ALLOWED_COUNTRIES` | `BR` | 422 `country_not_allowed` |
| Ages 18–65 and `age_min <= age_max` | | | 422 `audience_invalid` |

Committed rows are those with `created_at >= now - 7 days` and status not in `rejected` or `expired`. That includes `pending_approval`, so three pending requests cannot sneak past the cap. `failed`, `stopped` and `completed` still count, because money may already have moved. The sum uses `total_budget_cents`, not measured spend (spend can lag).

Settings are `Field(ge=0)` on `infrastructure/config/settings.py`. Every name is added to `deploy.yml`, `docker-compose.prod.yml` and `REQUIRED_ENV_NAMES`, with numeric defaults so an unset secret does not break settings parsing. `BOOST_REQUESTS_ENABLED` and `BOOST_ENABLED` must default to false on both surfaces. Update the parity rule-fires test (AE-0180): a seeded file that omits one new name exits non-zero.

### Tables

Revision `a8b9c0d1e2f3`, `down_revision = f9a0b1c2d3e4`. Idempotent. Bump `ALEMBIC_HEAD` again.

`boost_requests`: UUID pk; `idempotency_key` `String(128)` unique; `request_hash` `String(64)`; `media_id` `String(128)`; `status` `String(24)` with a check constraint; `objective`; `daily_budget_cents`, `days`, `total_budget_cents` check `> 0`; `currency` `String(3)`; `audience` JSONB; `reason` text; `score` float null; `created_at`, `expires_at` (`created_at + BOOST_APPROVAL_TTL_HOURS`, default 12); `decided_at`, `decided_by`; `telegram_message_id` bigint null; `notify_attempts` integer default 0; `starts_at`, `ends_at`; `meta_campaign_id`, `meta_adset_id`, `meta_creative_id`, `meta_ad_id` `String(64)` null; `launch_attempts` integer default 0; `next_attempt_at`; `last_insights` JSONB null; `insights_fetched_at`; `error_code` `String(64)` null; `updated_at`.

### State

`domain/boost_state.py`: a transition table and `transition()` raising `IllegalBoostTransition`. Each change is one `UPDATE ... WHERE id=:id AND status=:from` plus an event row in the same transaction.

```
pending_approval --owner approve--> approved --worker claim--> launching --four ids + ACTIVE--> active --now > ends_at--> completed
        | owner reject --> rejected                         | permanent error --> failed
        | now > expires_at --> expired                      | transient --> launching (retry, max 5)
                                                           active --owner stop (phase 3)--> stopped
                                                           active --ad DISAPPROVED--> failed
```

Terminal: `rejected`, `expired`, `failed`, `completed`, `stopped`.

There is no "approved and unclaimed for 2 hours" expiry. While `BOOST_ENABLED` is false the worker does not claim, and the approval stands until launch or until a later cap check rejects it at launch time (`failed` with `cap_failed_at_launch`, owner notified).

### Telegram

After the insert commits, send one plain-text message. If this process crashes first, the boost tick sends when `telegram_message_id` is null and `created_at` is older than 30 seconds, so it does not race the request that is still sending. A second send is skipped once the id is stored (`UPDATE ... WHERE telegram_message_id IS NULL`).

```
💸 Pedido de impulsionamento
Post: <permalink> (<product label>, <age>h)
Alcance <reach> (mediana <median>) · shares/100 views <rate> (mediana <median>) · saves/100 alcance <rate>
Orçamento: R$ <daily>/dia × <days> dias = R$ <total> · Objetivo: engajamento · BR 18–65
Motivo: <reason>
Semana: R$ <committed> de R$ <cap> comprometidos
Expira em 12h.
```

Buttons: `✅ Aprovar R$ <total>` and `❌ Rejeitar`. Format cents as `R$ 20,00`. Missing metrics render as `n/d`.

`callback_data`: `ap:bst:ok:<uuid>` and `ap:bst:no:<uuid>`. Byte length stays under `CALLBACK_DATA_MAX_BYTES` (64). Pattern constant `CALLBACK_BOOST_PATTERN`. Phase 2 does not register `stop`.

Wire `BoostOwnerActions` as another mixin on `OwnerActionService`. In `_on_callback`, call it in the same chain as thesis, cover and queue, and return when it handled the update. The owner check and `claim_update` stay in `handle`. Do not grow `handle`'s signature.

`BoostOwnerActions.handle`:

- Not a boost callback: return false.
- Row missing or not `pending_approval`: answer the existing "already handled" style text.
- Past `expires_at`: transition to `expired`, edit the message to say it expired.
- Approve: run policy again. On failure, transition to `rejected` is wrong (the owner said yes). Transition to `failed` with `error_code` set to the policy code, edit the message with that code, and do not leave it pending.
- Approve when policy passes: `approved`, `decided_at`, `decided_by` = actor id, edit the message, remove the keyboard.
- Reject: `rejected`, edit the message.

Answers and edits go through the existing deferred reply queue (`deliver()` after commit, `discard()` after rollback).

The tick expires `pending_approval` rows past `expires_at` and edits the stored message to `⌛ Expirado`.

The System User needs the ad account, the Page and the Instagram account assigned in Business Manager. Starting scopes: `ads_management`, `ads_read`, `business_management`, `pages_read_engagement`, `pages_show_list`, `instagram_basic`. If creative creation returns permission code 10, 200 or 294, the row fails with `meta_<code>_<subcode>` and nothing is activated. Add `pages_manage_ads` only if that error says it is required. Do not put this token in `integration_credentials` in v1.

### Launch

`infrastructure/meta_ads_gateway.py`. Protocol on the boost domain. Tests install it on `app.state` as `APP_STATE_ADS_GATEWAY`. Production code constructs it only inside the worker, never in the API-key routes.

Preflight, no spend:

0. `GET /{media_id}?fields=id,permalink,media_product_type,boost_eligibility_info` with the ads token. Missing id → `media_not_visible_to_ads`. Ineligible → `media_not_boostable`.
1. `GET /act_{id}?fields=currency,account_status,amount_spent,spend_cap,timezone_name`. `account_status` must be 1. Currency must match the row.
2. `GET /act_{id}/minimum_budgets` and refuse when `daily_budget_cents` is below `min_daily_budget_high_freq` (`below_meta_minimum`).

Then create, each `PAUSED`, persisting the id before the next call. On retry, skip a step whose id is already stored.

| Step | Call | Constants to confirm on the test account |
| --- | --- | --- |
| Campaign | `POST /act_{id}/campaigns` | `objective=OUTCOME_ENGAGEMENT`, `status=PAUSED`, `buying_type=AUCTION`, `special_ad_categories`, `is_adset_budget_sharing_enabled=false`. Name `AE boost <uuid8> <media_id>`. |
| Ad set | `POST /act_{id}/adsets` | `daily_budget` in minor units, `start_time` / `end_time` (`start + days`), `billing_event=IMPRESSIONS`, `optimization_goal=POST_ENGAGEMENT`, `bid_strategy=LOWEST_COST_WITHOUT_CAP`, `destination_type=ON_POST`. Targeting: countries and ages from the row, `publisher_platforms=["instagram"]`, positions `stream`, `explore`, `reels` only when that position fits the media type. Set `targeting_automation.advantage_audience=0` so the age and country bounds apply. |
| Creative | `POST /act_{id}/adcreatives` | `object_id=META_PAGE_ID`, `instagram_user_id=META_ADS_IG_USER_ID` (not `instagram_actor_id`), `source_instagram_media_id=media_id`. Omit call-to-action for engagement. |
| Ad | `POST /act_{id}/ads` | `creative={"creative_id": ...}`, `status=PAUSED`. |
| Activate | three `POST`s | campaign, ad set, then ad, `status=ACTIVE`. Re-read `BOOST_ENABLED` immediately before the first of these. If it is false, leave the objects paused and the row `launching` is wrong: transition back is illegal, so stay `launching` with `next_attempt_at` deferred and do not activate. When the switch is on again, resume at activate because ids exist. |

The unverified payload keys (`special_ad_categories` empty list versus `["NONE"]`, advantage-audience field name, position list) live in `boost_constants.py`. The first test-account run is what fixes them. A permanent parameter error fails the row and pauses anything already created.

Claim: `UPDATE ... SET status='launching' WHERE status='approved' AND (next_attempt_at IS NULL OR next_attempt_at<=now)`. One row per tick.

Errors, same classification style as `InstagramGraphError`:

- Transient: HTTP 5xx, timeouts, codes 1, 2, 4, 17, 32, 341, 613, 80004, or `is_transient: true`. `next_attempt_at = now + min(2^n * 60s, 1h)`. After `BOOST_LAUNCH_MAX_ATTEMPTS` (5), `failed`.
- Permanent: 100, 190, 200, 10, 294, and budget/targeting subcodes. `failed` immediately, `error_code=meta_<code>_<subcode>`.
- If `x-business-use-case-usage` or `x-ad-account-usage` reports `estimated_time_to_regain_access > 0`, defer instead of counting a hard failure.

On failure after a partial create, pause the campaign (best effort), keep the ids, notify the owner. The bot sees `error_code` only.

Poll `GET /{ad_id}?fields=effective_status,ad_review_feedback`. `DISAPPROVED` → pause the campaign, `failed` with `ad_disapproved`, notify with the feedback summary and no raw token.

Stop (this phase adds `ap:bst:stop:<uuid>`): from `active` only, `POST /{campaign_id}` `status=PAUSED`, then `stopped`. A kill switch flipped while active does not auto-pause existing ads; the owner pauses those in Ads Manager or taps Stop. The switch blocks new activations only. Say that in the runbook so it is not a surprise.

### Insights poll

For `active` rows whose `insights_fetched_at` is older than `BOOST_INSIGHTS_POLL_MINUTES` (60): `GET /{ad_id}/insights?fields=spend,reach,impressions,frequency,clicks,cpm,actions&date_preset=maximum`. Store spend converted to integer cents on `last_insights`. If `date_preset=maximum` is rejected for a running ad, switch the constant to an explicit `time_range` from `starts_at` to now. `GET /boost-request/{id}` reads this JSON and never calls Meta.

When `now > ends_at + 1h`, read once more, transition to `completed`, and send the owner a one-line summary (spent, reach).

### Logging

Structlog events `boost.launch` and `boost.insights`. Extend `log_redaction.py` with `appsecret_proof=` next to the existing `access_token=` pattern. A unit test captures logs and asserts the token string is absent.

## Security

- API-key handlers do not receive the ads gateway. A review of the route's dependencies should show the worker as the only caller.
- Approval requires the webhook secret, a claimed update id, `is_owner`, and the boost regex. Other chats log `ignored=not_owner` and write nothing.
- Both kill switches default off. `BOOST_ENABLED=false` means the ads client is not called. Test that with a counter on the double, not by mocking the method under test into a no-op that could hide a call.
- `reason` is control-stripped and length-capped. Plain text, so there is no HTML injection surface.
- Audit detail is an allowlist. Responses to the bot use stable codes.

## Testing

Gherkin first, in the two feature files named above. Unit tests reference the scenario titles.

Pure: metric tuple per product type; deprecated names absent; rates and medians with nulls and zeros; each policy boundary; legal and illegal transitions; callback regex; idempotency hash.

Gateway (respx): media pagination stops at `since` and at the page cap; insights fallback on 400; ads happy path is paused through four creates then three activates; resume skips completed steps; transient versus permanent; usage-header deferral; kill switch performs zero HTTP calls; token absent from logs.

API (httpx plus `app.state` doubles): 401, 503, query 422, idempotency 202/200/409, duplicate media 409, cap 422, list filters, GET does not invoke the ads double.

Webhook: owner approve and reject; stranger; duplicate update; expired tap; approve after the cap dropped.

Contracts: `make regen-contracts`. Env parity rule-fires test updated.

## Rollout and rollback

1. Ship phase 1. Run the scope probe with the production token in a shell. The bot may log proposals and must not call `POST /boost-request` yet.
2. Ship phase 2 with `BOOST_REQUESTS_ENABLED=true` and `BOOST_ENABLED=false`. Approve and reject in Telegram. Confirm no ads HTTP traffic.
3. Finish the Meta checklist. Point secrets at a test ad account. Accept ADR-0029. Run one boost at the product floor, 1 day. Confirm the campaign in Ads Manager, then raise caps.
4. First production boost: `BOOST_MAX_DAILY_BUDGET_CENTS=600`, `BOOST_MAX_DAYS=1`, one approval, then restore the defaults in this plan.

Rollback is `BOOST_ENABLED=false` and, if something is already active, Stop or Ads Manager pause. Migrations are additive. Do not drop the tables to roll back.
