## Where Chromium runs after P1

The worker runs every carousel phase, so the run's renders (HD included) are in the worker. The backend still renders
in the web process: the dashboard exports (`presentation/application/handlers.py`), finalize (`editorial_finalize.py`)
and the refinement and copy-refine renders (`refinement_service.py`, `refine_copy.py`). Moving those into the worker is
a separate change; P1 keeps the backend sized for them (Pedro, B3).

Every render goes through `export_slot` (`infrastructure/external/export_lock.py`): an asyncio lock in the process,
then a Postgres advisory lock held on its own connection. The worker opens the same app engine (`attach_db`), so the
slot spans both containers: **at most one Chromium export runs on the box at a time**, whichever container asks.

The other case (the worker rendering, the backend at its web peak 361) is 700 + 1222 + 361 + 995 = 3278, ≈ 638 MiB
headroom. The sum takes each container's own peak, not a coincident sample, so it is conservative. Without the shared
export slot (both rendering at once) it would be 700 + 1222 + 1222 + 995 = 4139 MiB, over RAM: the slot is what makes
the 1600M caps safe, and swap (2 GB, 103 MiB used today) absorbs the backend's overshoot, never the worker's.

## Worker numbers after the 2026-10-26 runs (AE-0555)

**Prod, 2026-10-26 (pgq jobs 24-28, one at a time, 1600 MiB cap).** The worker's `memory.current` after each
run went 669 → 843 → 858 → 925 → 966 → ~1035 MiB. `memory.peak` reached 1408 MiB in job 24's images/export and
the 1600 MiB cap in job 28. `memory.events` showed `max=83` and `oom_kill=0`. Every step-up happened in images/export.

The cgroup counts page cache, not only process memory. Each run writes 116-224 MB of carousel files (slides,
HD slides, PDFs, artifact staging and promoted copies) and never reads them again, and Linux charges that
cache to the writer's cgroup. The per-run steps (+174, +15, +67, +41, +69 MiB) are no bigger than what each
run writes. `max=83` with no OOM kill is the kernel reclaiming that cache at the cap. The fresh worker after
Pedro's restart: anon 232 MiB, file 88 MiB.

**Measured in the prod image** (Python 3.11, headless shell, 1 CPU, 1600m cap, `/tmp` tmpfs;
`backend/scripts/measure_carousel_export_memory.py`, 8 cycles of a 10-slide PT+EN carousel, images +
standard and HD export + PDF + artifact activation, outputs kept):

| | before the fix | after the fix |
|---|---|---|
| Worker cgroup between cycles | 461-493 MiB | 348-383 MiB, flat |
| Run's files still in page cache (`mincore`) | 119-147 MiB | 0 MiB |
| Python process anon / tracemalloc | 234-244 / 3-10 MiB | 237-247 / 3-10 MiB |
| Cycle peak (cgroup) | 1109-1159 MiB | 1029-1096 MiB |

In these side-by-side runs the Docker Desktop VM (3.9 GB, shared with other containers) evicted older runs'
cache through its own reclaim. An earlier before-run, made while the VM had memory to spare, piled up the
way the droplet did: 361 → 643 MiB idle, peak 980 → 1297 MiB. The `mincore` column is what each run leaves
behind either way.

**What bounds the peak now.** Headless Chromium's HD render is about 650-700 MiB over the worker's idle
baseline (renderer plus display compositor; standard export about 480). It barely grows with the slide count:
3 slides 660 MiB vs 10 slides 700 MiB. `--disable-gpu`, `--disable-software-rasterizer`,
`--num-raster-threads=1` and a device scale factor of 1 did not lower it. The worker's own peak is therefore
about Python 250 + Chromium 700 + Chromium's mapped files about 100 ≈ **1050-1100 MiB**, under the 1600m cap
with about 500 MiB of margin. The cap stays as it is.

**To confirm on prod:** after the deploy, the first runs should show the worker's `memory.stat` `file` back
near 100 MiB between runs and `anon` flat. If `anon` grows run after run, that is a separate retention
outside images/export.
