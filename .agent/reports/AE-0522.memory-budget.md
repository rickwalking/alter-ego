## Where Chromium runs after P1

The worker runs every carousel phase, so the run's renders (HD included) are in the worker. The backend still renders
in the web process: the dashboard exports (`presentation/application/handlers.py`), finalize (`editorial_finalize.py`)
and the refinement and copy-refine renders (`refinement_service.py`, `refine_copy.py`). Moving those into the worker is
a separate change; P1 keeps the backend sized for them (Pedro, B3).

Every render goes through `export_slot` (`infrastructure/external/export_lock.py`): an asyncio lock in the process,
then a Postgres advisory lock held on its own connection. The worker opens the same app engine (`attach_db`), so the
slot spans both containers: **at most one Chromium export runs on the box at a time**, whichever container asks.

## Budget (RAM 3916 MiB), worst case

| | MiB |
|---|---|
| Other containers at their own peaks (opencode 392, frontend 155, postgres 75, certbot 56, redis 15, nginx 7) | 700 |
| Backend rendering an export (run peak) | 1222 |
| Worker inside a run, between exports (in-run baseline) | 545 |
| Host outside the containers (today) | 995 |
| **Total** | **3462 → ≈ 454 MiB (12 %) headroom** |

The other case (the worker rendering, the backend at its web peak 361) is 700 + 1222 + 361 + 995 = 3278, ≈ 638 MiB
headroom. The sum takes each container's own peak, not a coincident sample, so it is conservative. Without the shared
export slot (both rendering at once) it would be 700 + 1222 + 1222 + 995 = 4139 MiB, over RAM: the slot is what makes
the 1600M caps safe, and swap (2 GB, 103 MiB used today) absorbs the backend's overshoot, never the worker's.
