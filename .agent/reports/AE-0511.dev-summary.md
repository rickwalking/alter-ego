## Summary

Implements Pedro's decision (2026-10-31). One additive column `users.must_change_password` (`BOOLEAN NOT NULL DEFAULT
false`). `AdminUserHandler.reset_password` stores the temporary hash through `User.reset_password` (flag on); the
self-service change (`AuthCommandHandler.change_password` and `UserService.change_password`, both via
`new_password_hash`) stores the new hash through `User.change_password` (flag off). Enforcement is in the
user-resolving dependencies: `require_signed_in_user` (no flag check) backs only `/api/auth/me` and
`/api/auth/change-password`; `require_authenticated_user` (and so `require_admin`/`require_editor_or_admin`) and
`roles.get_current_user` (`AdminUser`/`EditorUser`) answer 403 `{"detail": "Password change required", "code":
"password_change_required"}` while the flag is set; `get_optional_user` treats a flagged user as anonymous. Logout
needs no auth. `/me` returns `must_change_password`. change-password: wrong current → 401 `current_password_incorrect`
(same status/detail as before, code added), new == current → 400 `password_unchanged`, too short → 422 (unchanged),
limited to 5/minute like the login; nothing is written on any error.

Schema delivery: Alembic revision `b9c0d1e2f3a4` (on `a8b9c0d1e2f3`, idempotent, skips a database without `users`) and
the one-shot `python -m rag_backend.scripts.must_change_password_column --apply --verify`, run by `deploy.yml` right
after the insight columns step and before `up -d`, exit captured in `MUST_CHANGE_PASSWORD_EXIT`, the job failing at the
end through `ONE_SHOT_FAILED`. The existing post-stack-up `check_drift_cli` loop covers the new ORM column. DDL:

```sql
SET LOCAL lock_timeout = '5s';
ALTER TABLE users ADD COLUMN IF NOT EXISTS must_change_password BOOLEAN NOT NULL DEFAULT false;
```

Frontend: `/dashboard/account/password` (pt/en, title "Change password"/"Alterar senha"), linked from the sidebar
footer; the form checks length, confirmation and "differs from current" before sending, and translates every API
refusal. `PasswordChangeGate` in the app shell keeps a flagged user on that page (other dashboard/admin content is not
rendered); `api-client` sends any 403 `password_change_required` there (also for owner-only calls). After a forced
change the session query is refreshed and the user goes to `/dashboard/chat`. The reset dialog already showed the
temporary password only once; its copy now says so and that the user must change it at the next sign-in.

## Deviations / open concerns

- Added rule: a new password equal to the current one is refused (400 `password_unchanged`), so a temporary password
  cannot be kept by "changing" it to itself. Not in the decision; easy to drop if unwanted.
- Users an admin creates with a generated password are not flagged (the decision covers resets only).
- The flag is read from the database per request, not a JWT claim: the Next.js middleware cannot see it, so the
  forced redirect is client-side (shell gate + api-client); the API is the real guard.
- An admin who resets their own password is flagged too and must change it before using the admin area.
- Existing sessions of other devices stay valid after a change (out of scope).
