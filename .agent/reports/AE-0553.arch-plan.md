# Architecture Plan: AE-0553 — Isolate daily recovery items

**Date:** 2026-10-25
**Status:** Ready for development
**Tier:** T2

## Goal and root cause

The daily recovery scan must finish when one dead-letter revive raises, and the failed item must retain its one recovery attempt. The scan currently commits `recovery_attempt` in `SqlRecoveryStore.mark_attempted`, then revives through `AutopilotQueueBridge` in a second transaction. An exception therefore stops the scan after consuming the attempt.

## ADR check

No new ADR. This implements the transactionality and at-least-once recovery guarantees of ADR-0026 without changing the queue technology, schema, API, or deployment model.

## Options

1. Clear the marker in a compensating transaction after an exception. Rejected: a process crash between the failed revive and compensation still consumes the attempt, and an uncertain commit can cause a later duplicate.
2. Mark and revive in one SQLAlchemy session. Chosen: both writes commit or roll back together, existing CAS operations remain the concurrency fence, and the change stays within the current bridge.
3. Move the operation into a database function. Rejected as unnecessary schema and deployment complexity for a small follow-up.

## Design

- `DailyRecoveryScan` catches exceptions around each dead-letter revive, records a bounded failure reason, emits one structured warning with only generation-run id, autopilot-run id, and exception type, then continues with the remaining items, stale recovery, purge, counts, and summary.
- `ScanReport` carries failed items. `summary_text` appends each reported item's autopilot-run id and bounded reason without including run payloads or prompt text in logs.
- `ParkedAutopilot.revive_dead_letter` receives the whole `ParkedDrive`, so the queue bridge can atomically mark the exact generation row and revive its autopilot run.
- The bridge locks the autopilot row first, matching the owner retry's write order and fencing concurrent owner retries. It then locks and marks the generation row through the generation-queue public facade and calls the existing session-scoped revive. One commit covers the marker, autopilot transition or replacement run, generation-run requeue, notice ledger, audit, and outbox rows.
- A second scan sees either the committed resolved state or an already-marked row and does not revive again. An exception exits the session before commit and restores both rows, allowing the next scan one retry.
- No schema, migration, deploy one-shot, feature flag, or new runtime component.

## Testing

- Unit: several items with one raising; later items still revive, purge and summary still run, the failed id and reason appear, and the log contains ids and error type but no exception/payload text.
- Integration: inject a one-time revive failure and verify marker and run state roll back, then the next scan succeeds once.
- Integration: concurrent scans produce one successful revive; a concurrent real Telegram owner retry and scan also produce one successful revive.
- Existing recovery, Telegram retry, and queue integration tests remain regression coverage.

## Rollout and rollback

Normal PR deployment. Rollback is a revert; there is no persistent format or schema change.
