## Findings

**MAJOR (external) — the pin was downgraded from a digest to a mutable tag.**
The old reference was immutable (`minio/minio@sha256:14cea…`). The replacement,
`quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z`, is a **tag**: a repush at quay
silently changes what prod runs. Using a tag was the right call under incident
pressure (the digest was unknown and the registry was the thing being worked
around), but it should not stay. Re-pin by quay digest now that the tag resolves.
→ **AE-0344**.

**MAJOR (external) — the dev compose still points at the dead Docker Hub repo.**
`docker-compose.yml` still references `minio/minio:latest` and `minio/mc:latest`.
Those are the same images Docker Hub removed, so **every developer pull and every
fresh onboarding hits the identical `pull access denied`** — and `latest` is
unpinned besides. The ticket's "any other image pin" non-goal reasonably excludes
unrelated images; it does not cover leaving *the same broken image* in the tree.
→ **AE-0345**.

**MINOR (external) — the root cause survives, by design.**
`.github/workflows/deploy.yml` still runs `compose down` immediately before
`compose pull`, so any future pull failure on any image reproduces the full
outage. This was an explicit, correctly-reasoned non-goal of this ticket — the
blast radius is simply unchanged as of this PR. → already ticketed as **AE-0333**.

**Verified, no finding:** the pinned tag is the exact release that was running
(`minio --version` in the live container and the local image labels agree);
`compose config --images` lists the quay reference for both `minio` and
`minio-init`; `compose pull --dry-run minio` succeeds on the droplet; prod
re-verified during this review at 10 containers Up and `https://marinssolutions.com/`
→ 200.
