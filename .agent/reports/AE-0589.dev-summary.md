Status: Dev Complete

## Summary

The backend trusts `X-Forwarded-For` only from nginx (Pedro's decision, 2026-11-01). nginx gets the fixed address
`172.18.200.10` on the pinned prod network (`172.18.0.0/16`, dynamic addresses from `172.18.0.0/17` only); the
backend sets `FORWARDED_ALLOW_IPS: "127.0.0.1,172.18.200.10"` and runs uvicorn with `--proxy-headers`. nginx reads
the visitor from `CF-Connecting-IP` when the peer is a Cloudflare range and sends `X-Forwarded-For $remote_addr` on
every location (no more appending the client-supplied header). Login and change-password now get one bucket per
visitor; nginx's own `limit_req` zones become per visitor too (they keyed on Cloudflare edges).

## Deploy Notes

The deploy already runs `down` (removes the network) then `up` (recreates it), so the pinned subnet and nginx's
address apply inside the usual blip; no extra downtime. The subnet is the one prod already got, so it is free once
`down` has removed the old network. If something else on the droplet held `172.18.0.0/16`, `up` would fail with a
pool overlap; check with `docker network ls` / `docker network inspect` before merging if unsure.

## Residual

- The no-JavaScript `/auth/login` route (Next.js) calls `backend:8000` directly and does not forward the visitor, so
  those attempts share the frontend container's backend bucket; nginx's per-visitor `limit_req` on `/auth/login`
  covers that path. The frontend is not trusted.
- Cloudflare's ranges are inlined in both nginx configs; refresh them if Cloudflare publishes new ones.
