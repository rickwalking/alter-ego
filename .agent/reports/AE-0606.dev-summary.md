### Review round 1 fixes
- The finish toast no longer depends on event order. The backend publishes `phase_changed(in_progress)` and `run.started`
  before the 202 returns, so the old status-edge watch could stay at "accepted", lose the toast and fire it for a later
  run. The watch now holds the version the Retry moved past (the `expected_version` of the accepted POST). Only a state
  past that version counts, and the first stop ends the watch, with or without a toast.
- That removes the "idle", "accepted" and "running" states altogether, so there is nothing left to move to `RETRY_*`
  constants: the watch is a `number | null`.
- The watch uses the sent version rather than the 202's `lock_version`, because that field is nullable in the contract.
- A status that is not an outcome (for example `approved`) ends the watch silently. A run that carries on past such a
  status gets no finish toast; a missing toast is the safe side of a wrong one.
- The capability is no longer polled while `phase_status` is `in_progress`. Other temporary refusals still poll.
- The failed card's restart is primary whenever there is no recovery action, so "Start over" leads when Retry is refused
  or hidden.

### Review round 2 fixes
- An accepted Retry reads the workflow state again once more when the first read fails. The stream carries no lock
  version, so without a read the state never moves past the watched version and the watch could only end on a later
  run's state (a late or wrong toast). After two failed reads the watch is dropped: no finish toast, never a wrong one.
- Two scenarios added (32 in the feature file): a retry whose state cannot be read again watches no run, and one whose
  first read fails still says how it ended. Both tests failed before the fix (the second read never happened).
- Round 1's "Tests Run" counts (24 files, 214 passed) predate round 1. Round 1 ran 67 files, 507 passed; round 2 ran
