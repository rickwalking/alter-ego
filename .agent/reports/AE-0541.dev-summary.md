Status: Dev Complete (pending PR CI)
Owner: Pedro

## Summary

The signed-off checkpoint prune never matches a carousel with a generation run in a held state. `HELD_STATUSES`
(`generation_queue.constants`) = `ACTIVE_STATUSES` (queued, running, retry_wait) + `dead_letter`;
`project_has_held_run` (`generation_queue/infrastructure/run_fences.py`, re-exported by `public.py`) is the SQL
`EXISTS` fence; `checkpoint_prune._eligible_projects` adds `~project_has_held_run(model.id)`, so the dry run and the
locked `--apply` re-check share it. `project_has_active_run` moved to the same module (same SQL; its caller, the
stale-run reaper, is unchanged) to keep `public.py` under 400 lines.

## Acceptance Criteria Implemented

- [x] AC1 held-state runs (queued, running, retry_wait, dead_letter) keep their carousel out of the dry run; succeeded
  and cancelled runs do not.
- [x] AC2 a queued run that appears after the dry run makes `--apply` refuse, delete nothing and write no backup.

## Known limits

`FOR UPDATE` locks only `carousel_projects` rows, so a run enqueued in the instant after the locked re-check is not
seen (same as the autopilot guard); the latest checkpoint is always kept, so such a resume still works. A dead-lettered
run blocks the prune of its carousel until it is recovered or cancelled (intended).
