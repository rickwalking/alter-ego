# Developer Completion Report — AE-0598

Ticket: AE-0598 — A deploy drains the generation worker and fits its timeout
Status: Dev Complete
Owner: Pedro Marins

## Summary

Pedro's decision (2026-11-02): drain plus a timeout margin.

- Worker drain: a drain flag (`/tmp/generation-worker.drain`, the worker's own tmpfs) and a busy marker
  (`/tmp/generation-worker.busy`, present while a generation job is in the entrypoint, set before the drain check).
  While the flag is fresh the entrypoint raises `RetryRequested(30 s)` before the handler (run not claimed, no
  attempt counted) and a drive yields at its next phase boundary (`drive_stopping`, same path as SIGTERM). The flag
  expires after 900 s and the worker removes flag and marker at start. `python -m rag_backend.worker.drain_cli
  drain|idle|clear` is the deploy's handle.
- Deploy: `scripts/deploy/drain-generation-worker.sh drain docker-compose.prod.yml 240 5` after the build, then
  `stop -t 60` (240 + 60 = the old 300 s), `down` as before; `clear` after `up -d` as a warn-only backstop. The
  script always exits 0 (usage error 2). `command_timeout: 15m`. No check removed.
- opencode: `init: true`. Root cause: opencode is PID 1 (prod `docker top`: one process, no init); the entrypoint
  already `exec`s, and PID 1 never gets a signal it has no handler for, so SIGTERM was dropped. Local proof with the
  image built from `ops/opencode` and prod's flags: `docker stop -t 30` took 30.1 s, exit 137 (SIGKILL) without
  init; 0.13 s, exit 143 (SIGTERM) with `--init`.

When the bound runs out: the drive is killed as before; its row stays `running`, its PgQueuer job stays `picked`,
PgQueuer re-picks it after `--heartbeat-timeout 300` and the drive reaps the orphaned phase and re-runs it from the
last checkpoint (AE-0522 scenario "A run interrupted by a deploy resumes by itself").

## Deviations / open concerns

- The deploy reads idleness from the worker's busy marker, not from `psql` on `generation_runs`: a stale
  `running` row of an earlier kill would hold the wait to its bound, and the marker cannot be passed by a job.
  So the dry run stubs `docker` only (no `psql`).
- Most phases outlast the 240 s bound (outline p50 975 s on prod): the drain saves short phases and stops new
  pickups; a long phase is still killed and resumed from its checkpoint, ~5 min after the new worker starts.
- Maintenance jobs and the periodic steps are not drained (short, commit per step).
- A targeted local combination (`tests/unit/scripts_ci` + `test_generation_queue_pg_ae0522.py`) shows an
  unraisable unclosed event loop warning landing on a random test; it reproduces with main's versions of the
  changed files, so it predates this ticket. The full gate run was green.
