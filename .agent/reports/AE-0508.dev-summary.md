### Summary
"Gerar capa com Grok" (Pedro's decisions, 2026-10-22 and 2026-10-23): on the publish step of a Ponto de
Vista carousel the owner ticks 1-3 of their library photos, writes a direction and confirms a dialog that
names xAI, the photo count and the caps. The backend records a `pending` generation and runs the Grok Bot
job in a tracked background task. The photos are re-encoded (PNG, at most 1024 px, no metadata) and ride
the **existing** image bridge webhook as two optional keys (`task: "image_edit"`, `reference_images`);
the callback is unchanged and text-only jobs keep the exact old body (Pedro: the Grok Bot side already
takes image requests through its sidecar). The answer is fitted to 1080x1350, passes the `ai_image`
cover rules and is stored as a private creator asset with role `cover`. It shows up in the cover picker
as `source: "generated"` and is picked through `PUT /api/carousels/{id}/cover` (stored as an `ai_image`
`slide_cover`); the library photos stay options, so the default slide 1 is one tap away.

Caps 4 per carousel and 40 per calendar month (UTC), counting pending + succeeded; failures are free.
One pending generation per carousel. The check and the insert run after locking the owner's user row.
Owner only (admins who do not own the carousel get 403). Every call is a row in
`carousel_cover_generations` (time, carousel, owner, prompt SHA-256, photo count, model, cost, status,
error code) plus a `cover_generation` log line (never the prompt text, bytes or URLs). Any failure
(webhook, bridge error/timeout, unusable image, unreadable photo) settles the row `failed` with a code and
stores nothing; a run lost to a restart is failed as `cover_generation_interrupted` on the next read.
Unconfigured bridge → 503 `cover_generation_unavailable`, nothing recorded. No feature flag (Pedro).

The prompt field is its own component (`CoverPromptField`, `value`/`onChange` + a `children` slot) so
the AE-0509 prompt suggestions can fill it.
