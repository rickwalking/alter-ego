## Developer Completion Report
Ticket: AE-0494
Status: Dev Complete

### Summary
The owner can delete a photo from the private creator photo library (Pedro's decision: a photo in use by
any carousel cannot be deleted until no carousel uses it; show which). `DELETE
/api/carousels/creator-assets/{asset_id}` (owner only, admins included as "not the owner") deletes the
row and its stored WebP (kept while another row points at the same bytes). A carousel that uses the photo
— as creator asset, slide-1 hook photo or slide-1 cover (`slide_cover`), the same references the cover
sweep checks — blocks it with 409 `{code: "creator_asset_in_use", carousels: [{id, title}]}`. The library
image route now answers 404 (was 400) for an unknown photo, so a deleted photo's URL is a 404. The wizard
"Foto do slide 1" gets "Excluir foto selecionada" with an inline confirm; a 409 lists the carousels with
links to their workspaces; deleting the selected photo selects the newest remaining one.

Review round 1: the asset row is read `FOR UPDATE` before the in-use check (a carousel that starts using
the photo waits on the row's key-share lock instead of losing it to the delete); GrokBot cover rows on the
asset (`autopilot_cover_assets`, pending topics included) count as uses and are listed as `topics` in the
409, and an asset with role `cover` is refused with 409 `creator_asset_cover_managed`; another owner's
photo now answers 404 like an unknown id; a failed unlink after the commit is logged with the asset id
and the delete still answers 204; the wizard resets the delete mutation when the selection changes.
