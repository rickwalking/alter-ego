### Summary
Hotfix for the 2026-10-14 prod incident: after the owner's Approve the run sat in
`publishing` with `state_reason=content_publishing_limit_unreadable` and never posted.
`content_publishing_remaining` called `GET /{ig_user_id}/content_publishing_limit` without
`fields`; on `graph.instagram.com/v23.0` that returns only `quota_usage` (no `config`), and
`quota_remaining()` required `config.quota_total`, so every read failed.

Fix:
- The quota GET sends `fields=quota_usage,config` (`PUBLISHING_LIMIT_FIELDS`).
- The parser falls back to Meta's documented 100 posts / 24 h
  (`DEFAULT_PUBLISHING_QUOTA_TOTAL`) when `quota_usage` is readable but `config.quota_total` is
  missing or not an int, and logs `instagram_quota_total_missing`. A body without a readable
  `quota_usage` still raises the transient `content_publishing_limit_unreadable`.
- Loop guard: the existing publish retry budget already fits (`PUBLISH_MAX_ATTEMPTS` = 3,
  backoff 60 s then 300 s): each transient quota error is recorded as an attempt and the third
  moves the run to `publish_failed` with the existing publish-failed notice (Retry offered).
  No new machinery; a new end-to-end test through the real gateway and publisher proves it.
