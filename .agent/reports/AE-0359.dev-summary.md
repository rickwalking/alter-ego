## What changed

- `deploy.yml` writes the autopilot environment into the server `.env`. Secret values may be empty on the first deploy. `CAROUSEL_PUBLIC_BASE_URL` is `https://marinssolutions.com`. `AUTOPILOT_ENABLED` falls back to `false` and `AUTOPILOT_DAILY_CAP` falls back to `1` when those secrets are unset.
- `docker-compose.prod.yml` passes the same names into the backend service. With the variables unset, `docker compose config` renders `AUTOPILOT_ENABLED: "false"`.
- `backend:autopilot-env` (`scripts/ci/check_autopilot_env_parity.py`) fails when deploy.yml and the backend service disagree on an autopilot variable, when the enabled flag does not default to false, when the public base URL is not the site origin, or when the daily cap has no numeric default. Seeded violations exit 1.
- The worker already skips `autopilot_runner.tick` when the flag is false (`test_run_tick_skips_autopilot_when_disabled`). This ticket makes the deployed default that false value.

## Deviations

- The architecture doc says `GROKBOT_API_KEY_HASH`. AE-0351 and this ticket use `GROKBOT_API_KEY_SHA256`, which is the setting the process reads. Wired `GROKBOT_API_KEY_SHA256`.
- `AUTOPILOT_ENABLED` and `AUTOPILOT_DAILY_CAP` are optional secrets with committed fallbacks `false` and `1`, so the first deploy stays off and an empty cap does not crash settings parsing. Pedro turns the runner on by setting the secret and redeploying. The gate rejects a committed default of `true`.
