## Developer Completion Report

### Summary
Pedro's review of #287 (AE-0551), five points, plus one defect found while fixing the first:

1. **Owner only.** The cover panel shows its form only once the owner's generation list has loaded. A
   403 shows the not-owner note, and the loading state shows nothing. Found while fixing this: the list
   read went through `apiCall`, whose 403 sends the browser to /403, so a non-owner lost the publish
   page (since AE-0508). The list now uses the new `apiCallOwnerOnly` (`lib/api-client.ts`), a GET that
   keeps the 401 login redirect but not the 403 page redirect.
2. **Upload errors by cause.** Each cause has its own message:

   | Cause | Message |
   |---|---|
   | `TypeError` (no HTTP answer) | "check your connection" |
   | 429 | "wait a minute" |
   | 5xx or anything unexpected | "try again" |
   | Other 4xx (type, size, validation) | the wizard's `create.photo.uploadFailed` |

   `apiUpload` turns a 2xx reply that is not JSON, or that misses fields, into `ApiError(500)`, as
   `apiCall` already does, so a stored photo is never reported as a network failure.
3. **Polling.** `useCoverGenerations(projectId)` drops the always-true argument. Two tests pin that the
   list is refetched on an interval only while a generation is pending. The interval already stopped
   otherwise, and the query client does not refetch on focus.
4. **One `uploadFailed` string.** `publish.coverPicker.generate.uploadFailed` is gone in pt and en; the
   panel reads `create.photo.uploadFailed`.
5. **Tick once listed.** An uploaded photo waits until the refetched cover options list it, then is
   ticked while fewer than 3 are ticked. Two uploads in a row are both ticked.

Also from the review: a failed refetch after a successful load keeps the owner's form, and the failure
causes are one `UPLOAD_FAILURE` constant.
