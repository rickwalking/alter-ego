### Summary
Three prod issues from 2026-10-15 (autopilot carousel `f21b2bdb`).

1. **Langfuse tracing gaps.** Root cause: the old `propagate_attributes` put the metadata on a
   *span*, not the trace, and the resume path (HTTP runner + autopilot) opened no phase span, so
   each LangChain callback generation started its own anonymous trace. The autopilot also labelled
   runs with the gate phase (`research` while generating the outline).
   Fix: `infrastructure/langfuse_phase_trace.py`
   - `phase_trace(metadata)` opens a span named `workflow_<phase>`, calls `update_trace`, and
     propagates the trace name, user, metadata and tags (Langfuse v3 `propagate_attributes`) to
     every generation inside it.
   - `workflow_trace_scope(WorkflowTraceScope)` is a contextvar actor scope.
   - Every trace carries the metadata `project_id`, `phase`, `agent_name`, `user_id`,
     `content_type` (missing values read `unknown`) and the tags
     `phase:<phase>`, `agent:<agent>`, `content:<content_type>`. Constants are in
     `domain/constants/langfuse_tracing.py`.
   Seams: the graph `ensure_artifacts` covers outline, content (incl. persona scoring and
   distribution), design and images; `start_workflow` covers research; the autopilot
   `owner_autofix` is covered too. The legacy `propagate_attributes` now delegates to
   `phase_trace`, so the blog paths get tags as well.
   Scope: `execute_resume_run` (both paths) sets the project and the owner via
   `open_run_trace_scope` (editorial facade). The autopilot driver sets `agent_name=autopilot`;
   the HTTP path defaults to `editorial_workflow`.
2. **Frontend healthcheck.** The probe `wget http://localhost:3000/api/health` failed because
   busybox resolves `localhost` to `[::1]` while Next.js listens on IPv4 (and `/api/*` is
   proxied to the backend anyway). The frontend image now sets `ENV HOSTNAME=0.0.0.0` and probes
   `http://127.0.0.1:3000/robots.txt` (served by Next.js itself, no redirect, no backend). The
   backend probe uses `127.0.0.1` too. New gate `backend:healthcheck-loopback`
   (`scripts/ci/check_healthcheck_loopback.py`, wired into `gates.sh`, so CI's full
   `gates.sh backend` runs it) fails on any compose `healthcheck:` or Dockerfile `HEALTHCHECK`
   that names `localhost`. Seeded-violation tests prove it fires (AE-0180).
3. **Run-heartbeat lock waits.** The holder is the run's own `db` session. `resume_workflow`
   flushed the phase sync (`CarouselProjectWriteOwner.sync_phase` → `UPDATE carousel_projects`),
   and the runner committed only at the very end. Finalize/export, review events, SSE and both
   stage beats (`VALIDATING`, `PERSISTING`, 2 s `lock_timeout` each) all ran under that row
   lock, which gives exactly two `carousel_run_heartbeat_failed` warnings per run.
   Ruled out:
   - No lock is held across the LLM call itself.
   - The autopilot tick commits before the run.
   - The HTTP route commits before scheduling the run.
   - `phase_progress` writes commit per snapshot.
   - The only `FOR UPDATE` calls (outbox, scheduled publish) don't touch this row.
   Fix: `resume_workflow` and `redrive_pending_phase` commit the sync at once
   (`_sync_and_release_row`). This also removes a latent self-deadlock in the stuck-revert path,
   whose separate-session UPDATE waited on the same uncommitted row with no timeout. The heartbeat
   SQL itself (SKIP LOCKED / jitter) is unchanged, because no remaining overlap holds the row. No
   migration.

### Relay round 2 (READY 5ca80dc3: one failure, plus extra scope)
1. **`test_redrive_runs_the_pending_node_and_syncs_the_row` (`object MagicMock can't be used in 'await' expression`).**
   `_sync_and_release_row` now awaits `CarouselProjectWriteOwner(db).commit()`, and the test patched
   the owner with a plain MagicMock. The fix is in the test double: `commit` is an `AsyncMock`, and the
   test now also asserts that the commit is awaited. No assertion was weakened. The code is correct:
   the real `commit` is async.
2. **Flaky `tests/integration/test_blog_post_management_ae0296.py` (owner-approved extra scope).**
   Reproduced in isolation on the Pi (1 failure in about 10 file runs), so neighbours and ordering are not
   the cause. Root cause: the fixture used `sqlite+aiosqlite:///:memory:`, which SQLAlchemy serves through
   a `StaticPool`, so every session shares ONE connection and one transaction. Instrumented SQL events
   showed a fire-and-forget outbox publish task (`UPDATE event_outbox … COMMIT`) and the deferred
   request-session teardown `ROLLBACK` running on that connection concurrently with `_set_post_fields`.
   A foreign ROLLBACK between the arrange UPDATE and its COMMIT discards the arrangement, so the post stays
   standalone/draft. That gives `204 != 409` on delete and `400 != 200` on unpublish (the status guard).
   The fix: a per-test file DB (`tmp_path / 'ae0296.db'`, the pattern the other integration safety-net
   tests already use), so each session has its own connection. No retries, no skips.
   Proof: 20/20 consecutive runs of the file, plus a stress run of the two failing tests (40×
   each), 80/80 passing. The full-suite run is relayed (the Pi notes forbid the full suite here).
   Follow-up, not fixed here: 17 other integration files still use `:memory:` with the same latent race.
   They should get a ticket that moves them to a file DB or a shared fixture.

### Relay round 3 (READY a171739c: 2 setup ERRORs in the PG heartbeat test)
1. **`PostgresSyntaxError: syntax error at or near "("` at fixture setup.** The fixture runs
   `create_all` over every model in an isolated schema. `DocumentModel.is_public` had
   `server_default=func.false()`, which SQLAlchemy compiles to `DEFAULT false()`, a call to a
   function that doesn't exist. This is a model bug that predates this ticket. Prod never hit it because
   the migration (`a1b2c3d4e5f6`) uses `sa.false()` and prod uses Alembic, not `create_all`. The fix uses
   `sqlalchemy.false()`, which renders `false` on PG and `0` on SQLite. No migration and no schema change.
   The regression test `tests/unit/infrastructure/test_model_ddl_postgres_ae0390.py` compiles every table
   for the PG dialect, plus a seeded `func.false()` case proving the check fires (AE-0180 style).
2. **Then `RuntimeError: ... attached to a different loop`.** The DB gates never got this far, so this
   showed up only once the DDL was fixed. `pytest.ini` sets `asyncio_default_fixture_loop_scope = session`,
   so the async `world` fixture opened its asyncpg connections on the session loop while the tests ran on a
   function loop. The fix pins the fixture to `loop_scope="function"`.
3. **Verified on a real Postgres 16** (a throwaway `postgres:16` container on the Pi, removed afterwards):
   `test_run_heartbeat_lock_pg.py` 2/2 and `test_autopilot_scout_failure_lock_pg.py` 1/1 pass.
   Negative control: with the `_sync_and_release_row` commit removed, `test_phase_sync_never_blocks_the_heartbeat`
   FAILS (the second session's UPDATE errors on the row lock), so the test really guards the fix.
4. The AE-0296 flake fix (a171739c) is still in place and unchanged.
