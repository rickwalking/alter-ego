Status: Dev Complete

## Summary

Implements Pedro's decision (2026-11-01) with token versioning. `users.token_version INTEGER NOT NULL DEFAULT 0`
(ORM, entity, Alembic `c0d1e2f3a4b5` as the single head, idempotent prod one-shot
`rag_backend.scripts.token_version_column --apply --verify` in `deploy.yml` before `up -d`, with the in-stack retry
and the end-of-job failure). Access tokens carry `tv`; a token whose `tv` differs from the stored version answers 401
`Invalid or expired token` like an expired token; a token without `tv` counts as 0 (no logout at deploy).
`User.change_password` bumps the version in the same Unit of Work write as the hash; the handler returns a fresh token
and `POST /api/auth/change-password` sets it in `access_token` with the login's cookie flags (still 204).

Review fixes: the change reads the user row \`FOR UPDATE\` (\`UserRepository.get_by_id_for_update\`, re-read past the
identity map) before the password check, so concurrent changes are serialised and the bump is atomic (Postgres tests:
two concurrent changes give 204 + 401 and version 1; two changes in a row end at version 2 with the first change's
token refused; a waiting writer is proven blocked by the lock). The \`max()\` write and its test are gone. The unused
\`UserService.change_password\` is removed. The one-shot skips the \`ALTER\` when the column is present (proven under a
held ACCESS SHARE lock).

  (no exceptions allowed) plus a seeded-violation test; unit tests per dependency; SQLite flow

  `POST /api/conversations`); Postgres flow and repository test (`test_logout_other_sessions_pg_ae0593.py`).

## Deviations / open concerns

- The AE-0511 flow tests that kept using the pre-change bearer token after a change now continue with the session
  cookie (like the browser); the old bearer is logged out by design.
- A bearer-only API client must log in again after a change (the route stays 204 without a body).
- The admin reset does not bump the version (out of scope). Recommended follow-up: bump it on reset too, so an
  attacker's session dies at the reset instead of sitting on 403 password_change_required until the user changes.
- `PostgresUserRepository.update` writes every field from the entity it was given (pre-existing): an unrelated update
  built from a user read before a change (e.g. an admin edit) can write back the old hash and version. Not solved
  here; separate follow-up ticket.
