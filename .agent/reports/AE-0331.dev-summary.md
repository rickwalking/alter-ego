## What broke

The merge of PR #87 (2026-09-15 10:57Z) triggered the auto-deploy on `main`.
`.github/workflows/deploy.yml` runs `compose down` and then `compose pull`; the
pull aborted with

```
Error response from daemon: pull access denied for minio/minio, repository does
not exist or may require 'docker login'
```

`set -e` stopped the script **after `down` and before `build`/`up`**. Prod went
from 10 containers to **zero** and `marinssolutions.com` answered **521 for
roughly 40 minutes**.

Docker Hub's `minio/minio` is no longer pullable at all — the pinned digest
(`sha256:14cea493…`), `latest`, and dated tags each fail `docker manifest
inspect`. `quay.io/minio/minio` serves the identical release
(`RELEASE.2025-09-07T16-13-09Z`, confirmed from the running container's
`minio --version` and the local image labels). Nothing in the repo changed to
cause this; the upstream registry did.

## What changed

`docker-compose.prod.yml`: the `minio` and `minio-init` services now reference
`quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z` — same release, pinned by tag,
pullable. That is the entire diff (2 files changed counting the ticket; 139 diff
lines total including the ticket body).

## Recovery performed by hand

All eight data volumes and the server `.env` were intact. The app tier was
restarted on the still-local images
(`up -d --no-build --pull never postgres redis backend frontend nginx certbot`),
then the Langfuse tier the same way (the MinIO image was present locally under
its digest). The synced compose file on the droplet was patched to the quay
reference so the next `pull` would succeed, and the new backend/frontend images
were built on the droplet from the merged #87 source and swapped in.

## Verification

- `docker compose -f docker-compose.prod.yml config --images` lists the quay

- `docker compose -f docker-compose.prod.yml pull --dry-run minio` → "Pulled" on

- The pinned tag is the exact release that was already running.
- **The next `main` deploy completed green** — PR #88's own merge deploy rebuilt

- Re-verified 2026-09-15 during this follow-up: 10 containers Up,

## Scope discipline

The **deploy ordering** (`down` before `pull`) is what turned a registry failure
into an outage. It was deliberately NOT bundled here — this ticket is the
registry fix only. The ordering now has its own ticket, **AE-0333**
(pull and build before down), created in this follow-up session.
