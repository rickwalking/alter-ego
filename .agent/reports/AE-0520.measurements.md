No container has CPU shares set; the backend has the default 64 MiB `/dev/shm` (the P0 Chromium flag
`--disable-dev-shm-usage` stops Chromium from using it).

Budget against 3916 MiB:

- The caps alone (3584 MiB) already sum to 92 % of RAM, so they do not protect the box: they only bound each
  capped service. The uncapped services (≈1.3 GiB idle) plus the kernel and Docker (≈1 GiB: host `used` 3020 MiB
  vs Σ containers 2047 MiB) leave ≈ 0.9 GiB available at idle.
- A carousel run needs its own peak on top of that, which today has to come out of the 0.9 GiB and swap. That
  peak is criterion 1, still unmeasured, so the budget cannot be closed yet.
- The plan's P1 worker cap (≤ 900 MiB) does not fit next to the current uncapped web tier without swapping.
  It closes only if P5 caps the web tier AND the observability stack shrinks: the Langfuse stack (langfuse 767 +
  worker 312 + ClickHouse 111 + MinIO 95 ≈ 1.3 GiB actual, 3.3 GiB of limits+uncapped) is the largest consumer
  on the box. Options for Pedro: lower the ClickHouse cap to 768 MiB and cap Langfuse web at 768 MiB, or move
  Langfuse off the box, or a 4 GiB → 8 GiB droplet. With numbers from #1 in hand this is Pedro's call.

## 3. Root cause of the 10-21 and 10-22 `escalated / run_stale` runs

**Cause: a production deploy stopped the backend container while the run's phase was executing in-process.**
Not memory, not the LLM provider.

Evidence (`event_outbox` rows, GitHub Actions deploy job logs):

| | 10-21 run `b58082fb` (carousel `219c8fc7`) | 10-22 run `2a6c6c09` (carousel `73bcb16a`) |
|---|---|---|
| Run moved to `generating` | 12:00:09 | 12:54:30 |
| Last gate approved by the runner | design, 12:20:54 (images phase starts) | outline, 13:00:02 (content drafting starts) |
| Deploy run | 39597508538 (12:10 → 12:27) | 39782467059 (12:56 → 13:23) |
| `backend-1 Stopping` → `Stopped` (10 s grace, then SIGKILL) | 12:26:50 → 12:27:00 | 13:22:30 → 13:22:40 |
| New backend started | 12:27:15 | 13:22:56 |
| Reaper: `generating → escalated (run_stale)` | 12:30:35 | 13:25:17 |
| `carousel_projects.run_epoch` | 1 (reaped once) | 1 (reaped once) |

In both cases the phase had been running 6 and 22 minutes when `docker compose down` stopped the container;
the heartbeat stopped, and ≈ 3 minutes after the restart (heartbeat stale after
`workflow_run_heartbeat_stale_seconds` = 180 s) the reaper parked the run and the autopilot escalated it. The
other run of each batch was not affected because it was waiting for the owner, not executing. The backend logs of
those windows are gone (the container was recreated by later deploys; json-file logs live with the container), so
the timeline is reconstructed from the outbox rows and the deploy logs above. No OOM in the kernel log.

Measured phase durations (autopilot carousels, last 14 days, `phase_changed` gaps; each row is the time from
that gate opening to the next gate opening, i.e. owner/runner approval + the next phase's generation):

| From gate | n | min | p50 | max |
|---|---|---|---|---|
| research → outline ready | 16 | 2.1 min | 4.7 min | 13.6 min |
| outline → content ready (drafting, translation, persona) | 15 | 8.6 min | 14.6 min | 461.7 min* |
| content → design ready | 15 | 1.0 min | 39.5 min* | 531.2 min* |
| design → images ready | 17 | 0.8 min | 6.2 min | 71.5 min* |
| images → final review ready (render + export) | 16 | 1.1 min | 1.6 min | 185.8 min* |

\* includes human waits (rework, escalations, overnight). The pure generation phases are 2–15 min (p50); the
longest unattended one is content drafting (p50 14.6 min).

Implications for P1 (derived from these numbers, not round ones):

- Deploys must not kill a running phase: the worker needs `stop_grace_period` ≥ the longest phase it may be
  in. With content drafting p50 ≈ 15 min, a 120 s grace cannot finish a phase; the worker must instead stop at
  the next checkpoint boundary and the job be re-delivered and resumed from the checkpoint (the plan's
  heartbeat-timeout re-queue). Lease/heartbeat: heartbeat every 60 s, lease 180–300 s, so a killed worker's job
  is re-delivered within ≈ 5 min.
- Until P1, the cheapest mitigation is operational: do not merge to `main` (auto-deploy) while an autopilot run is
  `generating` (11:05–13:30 UTC on batch days).

## 4. Side-effect inventory (graph nodes and runner steps)

Graph: `agents/carousel_workflow_graph.py` (brief → research → outline → content → design → images →
final_review → approved_hold). Node bodies only `interrupt()`; their pre-gate work runs in
`PhaseArtifactRunner.ensure_for_phase`. LangGraph replays an interrupted node from its top, so everything before
an `interrupt()` repeats on every resume of that gate. No Pinecone write and no Instagram call happens inside the
graph or the runner steps (Instagram publishing is the separate publish job, already CAS + claim based).

| Step | What it writes | Idempotent on replay? |
|---|---|---|
| outline / content drafting / persona scoring / distribution copy | LLM calls; slide rows and project fields overwritten in place; slides created only when none exist (unique index project+slide_number) | Yes (LLM cost only; content artifacts are parked and skipped on resume) |
| design tokens / design | `update_project` theme + tokens; slide rows from outline if none | Yes (overwrite; a crash mid-insert can leave a partial slide set) |
| images: provider call (OpenAI / Gemini / GrokBot bridge) | paid image generation; `images/slide_N.jpg`; `carousel_image_generations` upsert by `generation_key` | **Partly**: reused only once the record row is committed; a crash between the provider response and that commit pays again. GrokBot jobs are keyed by a random uuid4 and a timeout falls back to OpenAI while the Grok job may still finish (double charge) |
| finalize (after the images gate) | Playwright render, PDFs, content-addressed artifact build, `activate_build` CAS | Yes (content hash + CAS; a lost finalize is not duplicated) |
| start_workflow | scrape + LLM synthesis, checkpoint, outbox events | Yes (early return when the checkpoint exists) |
| resume wrapper | `lock_version` CAS, heartbeats fenced by `run_epoch` | Yes |
| resume: revise feedback note + `revision_count` | checkpoint `aupdate_state` before the resume | **No**: a re-issued revise duplicates the note and counts twice (can hit the revision cap early) |
| resume: feedback correction | LLM classification + `persona_corrections` insert | **No** (duplicate row) |
| resume: image revise | appends to `custom_visual_details`, committed | **No** (appends again, new prompt hash, new paid images) |
| resume: revision-cap notification | one notification row per admin | **No** |
| runner: create project | `carousel_projects` insert + staged cover/hook files, then `attach_project` CAS | **No**: create commits before the attach CAS; a crash in between leaves an orphan project and the next tick creates another |
| runner: state moves, ready notice | `autopilot_runs` CAS + outbox row in one transaction | Yes |
| Telegram review dispatch | album + keyboard sent before the ledger save | **No**: a crash after send and before save re-sends that revision's review |
| autofix / gate repair / slide fix / cover switch | LLM before the lock, then advisory lock + `lock_version` CAS, rows, checkpoint patch, content-addressed render | Yes (LLM spend not protected) |

Merge gate for P1 ("all external writes outboxed or CAS-claimed"): the seven **No/Partly** rows above. The ones a
re-delivered queue job would actually hit are the image provider call, the runner's create-project, the revise
feedback/correction writes and the Telegram dispatch; each needs a key by run + step (or an outbox row written in
the same transaction as the state change) before P1 merges.

## HD @2x decision (recommendation for Pedro)

Recommendation (pending the HD number from #1, which can only change it if HD turns out cheap): **drop HD @2x
from the autopilot path and render HD on demand** (a "Baixar HD" action on the carousel page, or when Pedro
publishes somewhere that needs it).

Why, from what is known today:

- HD is 2160×2700 at `deviceScaleFactor` 2: 4× the pixels of a standard slide, rendered by its own Chromium
  launch. Two of the four exports per finalize are HD, so dropping it halves the Chromium launches of a run and
  removes its largest bitmaps.
- The autopilot path does not need HD to publish: Instagram uses the standard `pt/slide_N.jpg` files and falls
  back to `pt/hd/` only when the standard ones are missing (`modules/autopilot/infrastructure/slide_files.py`);
  the story image does the same (`modules/publishing/application/story_image.py`); the PDFs are built from the
  standard export (`render_language`).
- The export itself already treats HD as optional (`render_language`: "if HD fails the standard slides are
  still available").

It is not a one-line change: the artifact health check requires the HD renders
(`application/services/carousel/artifact_health.py`, "HD rendered slide missing") and the artifact build
records HD files. Skipping HD for autopilot runs needs those to accept a build without HD (or a per-build "HD
not rendered" marker) plus the on-demand HD action. Decision: Pedro's; if accepted, a follow-up ticket (not
part of P0).
