## What changed

- `POST /api/autopilot/topics` accepts a `TopicBatch` of 1–3 `TopicProposal` objects. Unknown fields are rejected (`extra=forbid`). Length limits match the ticket. Each source must be an http(s) URL. A schema violation returns 422 and writes nothing.
- Every source URL must have been served by `GET /api/autopilot/signals` within the last 6 hours. The 30-minute bundle cache is shorter than that window, so served URLs are stored in `autopilot_served_urls`. A proposal with any foreign URL is rejected with `source_not_in_signals` and is not stored. Other proposals in the same batch are still considered.
- Free-text fields are stripped of control characters before hashing and URL detection. A URL or `www.` host in those fields rejects the proposal with `url_in_text`. Text that is blank after stripping is rejected with `empty_text`. Prompt-injection text in `brief` is stored unchanged.
- `signal_hash` is sha256 of the normalized title plus the sorted canonical sources. A repeated hash returns the existing candidate id and queues no new run. A title whose token Jaccard with any carousel topic from the last 60 days is at least 0.6 is rejected with `duplicate_topic`.
- Accepted proposals are stored as `topic_candidates`. Runs in `queued` are created only for the highest scores that still fit `AUTOPILOT_DAILY_CAP` (default 1) on the America/Sao_Paulo calendar day. When the cap is already full, candidates are stored and the response reason is `daily_cap_reached`.
- The response is `{accepted, queued, rejected:[{title, reason}]}`.

## Known risks

- The daily cap counts every autopilot run created that America/Sao_Paulo day, including runs this intake did not queue.
