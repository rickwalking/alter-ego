## What changed

- `POST /api/telegram/webhook` takes no JWT and no scout API key. The header `X-Telegram-Bot-Api-Secret-Token` must match `TELEGRAM_WEBHOOK_SECRET` in constant time, or the response is 401 and nothing is written. A matching secret always returns 200, including a bad body, a stranger, a duplicate `update_id`, and a handler error.
- The `update_id` is claimed in `telegram_updates` before the allowlist. A conflict returns without a second action. `callback_query.from.id` and `message.from.id` must equal `TELEGRAM_OWNER_CHAT_ID`; anyone else is ignored.
- Approve compare-and-sets `awaiting_owner` to `publishing`, resumes `approve` on `final_review`, then releases the carousel through `CarouselReleaseCommand`. Leaving the run in `publishing` is the enqueue for the Instagram job. A lost compare-and-set answers `already handled`. A failed approve or release moves the run to `publish_failed`.
- Rework sends the Text / Design / Images / Outline keyboard and a ForceReply. The pending phase is stored on the notice ledger, keyed by the owner. The run stays `awaiting_owner` until the feedback text arrives, then it moves to `reworking` and resumes `revise` with `structured_feedback.target_phase`. Text maps to the content phase. The runner then returns the run to `awaiting_owner`. A revision cap moves it to `escalated`.
- Reject moves the run to `rejected` and does not release the carousel. Retry compare-and-sets `publish_failed` to `publishing` and does not resume or release again.
- `python -m rag_backend.modules.autopilot.scripts.set_webhook <https-url>` calls Telegram `setWebhook` with that URL, the webhook secret, and `allowed_updates` of `message` and `callback_query`.

## Deviations

- Rework does not compare-and-set to `reworking` on the Rework tap. The runner treats `reworking` like `generating` and would send a still-open final review back to the owner before the revise. The phase keyboard and ForceReply stay in `awaiting_owner`. The compare-and-set happens when the feedback text arrives, immediately before `resume revise`. That matches architecture §3 (keyboard, ForceReply, resume, then the runner re-drives the gates).
- Pending rework is a `pending` object on the existing `telegram_message_ids` notice ledger. No new table and no Alembic revision.
- Enqueue means the run is left in `publishing`. The Instagram job from AE-0357 scans that state. This webhook does not call Graph.
- A failed approve cannot return to `awaiting_owner` (illegal transition). The run moves `publishing` → `publish_failed` with reason `owner_approve_failed`.
- `_autopilot_engine_factory` was decorated with `@asynccontextmanager` even though it returns a callable. The decorator made the value unusable as an engine factory, so the decorator was removed. The webhook and the runner now share that callable.
- Untrusted JSON is typed as `object`, matching the rest of the autopilot module.
- Webhook copy and header names live in `webhook_constants.py` so `constants.py` stays under 400 lines.
- The committed route snapshot gained `POST /api/telegram/webhook` after the gate capture. The capture skipped `backend:test`, so that assertion was not part of `GATES_JSON`. The snapshot test was re-run locally and passed.

## Known risks

- Revise runs in the request. Image regeneration can hold the webhook open. The `update_id` claim and the compare-and-set still make a Telegram retry a no-op.
- Retry after `owner_approve_failed` only re-enters `publishing`. It does not resume approve or release again, so a carousel that never became public can be handed to the publish job.
- The release adapter commits the session. A later Telegram reply error is logged and does not roll that commit back.
