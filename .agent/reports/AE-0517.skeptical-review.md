## Findings

### [BLOCKER] Worker memory budget contradicts the box's actual headroom; "fail the worker, not the box" is false in the ~860 MB–1400 MB band
- Assumption: A `mem_limit`/`memswap_limit: 1400m` worker "fails the worker, not the box", and the box can absorb a new container on ~860 MB available / ~190 % committed memory.
- Risk: Between ~860 MB and 1400 MB of worker RSS the worker is *not* killed — the kernel satisfies the worker by swapping out the **uncapped** services (backend, langfuse, postgres, frontend have no limits — verified in docker-compose.prod.yml:56-131, 299-347). On a 2 vCPU box, that swap thrash lands exactly on visitors' p95, the thing this ADR exists to protect. The cap only "works" at ≥1400 MB, i.e. after the damage window. Worse, the plan's own risk §8 admits HD export "may exceed 1.4 GB" — so the likely outcomes are either box thrash (below cap) or every HD export OOM-killed → retry → poison-guard dead_letter (above cap). The mitigation order is backwards: P5 (cap/reserve backend, frontend, langfuse, "measured first") lands *after* P1 enables the worker in prod.
- Impact: Visitor-facing latency regression or systematic HD-export failures — a regression of the primary goal, caused by the fix.
- Suggested mitigation: Make P5 (or at minimum: measured free headroom ≥ worker cap + explicit caps on langfuse/backend) a *precondition* of enabling P1, not a follow-up; set the worker cap to measured free headroom (likely < 1 GB), and decide HD export's fate (drop from autopilot path / render on demand) *before* pinning 1400m in the compose file. Consider that moving Chromium out of the backend does not reduce total memory demand — it relocates and adds ~150-300 MB idle.
- Open question for author: What is the measured RSS of a full 4-export (incl. HD @2x, 2800×3600) carousel run today, and what is the measured free-memory floor with the worker at that RSS plus an uncapped langfuse?

### [WARN] Headline claim "deploys of the web backend no longer kill runs" is contradicted by deploy.yml as it stands
- Assumption: Splitting generation into a worker container makes runs survive web deploys.
- Risk: The deploy does `docker compose -f docker-compose.prod.yml down` for the **whole project** (verified, .github/workflows/deploy.yml:234) then `up -d` (:304). The new worker is in the same compose file, so every deploy kills it mid-phase too. The real benefit is only "runs *resume* after ~300 s heartbeat expiry post-restart" — durability-by-checkpoint, not survival. Additionally, the 120 s `stop_grace_period` extends every deploy's blip, and no phase in §5 includes changing the deploy strategy (e.g. `up -d --no-deps backend`) or preserving the worker container.
- Impact: Oversold core benefit; chaos test "redeploy the backend mid-run" as written would expose this; deploy downtime grows.
- Suggested mitigation: Either add an explicit deploy-workflow change to P1 scope (worker not downed on backend deploys) or restate the ADR consequence honestly as "runs auto-resume after deploys" with the measured resume latency.
- Open question for author: Is changing deploy.yml's down/up to a per-service update in scope anywhere? If not, why is the "no longer kill runs" consequence in the ADR?

### [WARN] Core design guarantees rest on unverified PgQueuer API behaviors — only 2 of ~6 assumptions are acknowledged
- Assumption: (a) `enqueue()` can run **on the caller's connection/transaction** so the CAS + `generation_runs` insert + enqueue are atomic; (b) `dedupe_key` dedupes only pending jobs, so the "Tentar de novo" re-enqueue with the same key (`run:<id>:start`) is accepted; (c) enqueue supports a **delay** for the advisory-lock tail re-enqueue; (d) `heartbeat_timeout` is configurable to 300 s; (e) stale-heartbeat requeue attempt accounting (acknowledged); (f) strict FIFO holds under `concurrency_limit` + requeues.
- Risk: The packet itself admits docs gaps for (e) and jitter only. If (a) is false, the "rolled-back CAS leaves neither" guarantee is unimplementable and you get the classic dual-write (CAS committed, enqueue lost → run silently never starts until the 04:00 scan). If (b) is false, the dead-letter Retry button silently no-ops. None of these can be verified from this repo (PgQueuer is not yet a dependency).
- Impact: The plan's three most-visible guarantees (exactly-once enqueue, retry button, no-duplicate-run) are each one wrong library assumption away from not working.
- Suggested mitigation: Add a P1 gate: a written verification matrix against the **pinned version's source** (not docs) for a-f, with integration tests that fail on semantic mismatch; treat "in-house SKIP LOCKED fallback" as more than a sentence — it is the contingency for every one of these.
- Open question for author: Has anyone confirmed PgQueuer accepts an external transaction for enqueue, and how its dedupe_key interacts with completed/held jobs on re-enqueue?

### [WARN] Rollback / flag-off leaves a dual-owner window; "PgQueuer jobs stay in their tables (harmless)" is asserted, not argued
- Assumption: Flag off → the web in-process runner resumes and queued PgQueuer jobs are inert.
- Risk: The plan does not define flag semantics: does the worker stop *mid-job* on flag flip? Who finalizes a `generation_runs` row left `running`? During flag-off, the in-process runner drives `autopilot_runs` while stale jobs (and their dedupe_keys) sit in PgQueuer; on re-enable, the recovery scan's step 1 ("queued runs with no active job → enqueue") races the in-process runner's own `queued` selection. The rollback narrative ("replayed by the in-process runner's existing `queued` selection" — runner.py:186-206 confirmed) papers over the handoff.
- Impact: A rollback under pressure (the exact scenario rollback exists for) can double-drive a run or strand rows in `running` forever.
- Suggested mitigation: Specify flag semantics at job granularity (drain-then-stop; worker owns rows to terminal state), and add a Gherkin scenario "flag flipped off and back on mid-run produces exactly one completed run".
- Open question for author: What exactly does the worker do with an in-flight job when `GENERATION_QUEUE_ENABLED` flips to false, and who writes the final `generation_runs` status?

### [WARN] A failed `pgq install` one-shot, under the "stack comes up anyway" pattern, breaks the Telegram approval path — and stacks a third DDL one-shot on an ADR-012 conflict
- Assumption: The palette_timestamptz pattern (deploy.yml:287-301 — exit captured, stack always up, job fails at end) is safe to reuse for queue DDL.
- Risk: With enqueue inside the CAS transaction (by design), missing/corrupt pgq tables make every Confirmar/Aprovar webhook roll back its CAS — the approval flow 500s until an operator re-runs the one-shot. The prior one-shots (blog cutover, palette) degraded a subsystem; this one takes out the owner's primary interface. Separately: the packet states "prod applies schema with create_all" as fact (true today — deploy.yml:255-262, migrations disabled on two unreconciled Alembic heads) while ADR-012 (accepted, per root CLAUDE.md) says the opposite; ADR-0026 neither supersedes ADR-012 nor resolves the drift it compounds. Also unspecified: with a same-image worker, do *both* containers run `create_all` at boot (concurrent DDL race on first deploy)?
- Impact: DDL failure converts to a functional outage of the morning approval batch; governance drift makes the next schema change riskier.
- Suggested mitigation: Make the one-shot failure mode fail-*closed* for enqueue (health check gates enqueue paths with a clear Telegram error instead of rolled-back CAS), mark ADR-012 superseded/amended in ADR-0026, and state which process owns `create_all` in the two-container topology.
- Open question for author: What does Pedro see at 08:05 if `pgq upgrade` failed at 03:00 and he taps Confirmar?

### [WARN] Over-cap backlog can grow without bound, and the advisory-lock re-enqueue breaks the promised strict FIFO
- Assumption: Over-cap themes roll to "next day's slot"; strict FIFO is a Pedro decision; a blocked job is "re-enqueued with a short delay".
- Risk: `AUTOPILOT_DAILY_CAP` defaults to 1 (deploy.yml:173) while Grok Bot delivers 1-3 topics/day — the backlog grows up to ~2/day with no max size, no oldest-first expiry, and "Aprovar todas" amplifies an ever-growing batch. There is no policy for what happens when the backlog exceeds a week. Also: re-enqueueing a lock-blocked job necessarily sends it to the queue **tail** (or requires priority, which was explicitly rejected) — either FIFO is violated or the head job spins; the plan asserts both strict FIFO and tail re-enqueue simultaneously.
- Impact: Degrades into an unbounded, stale, mis-ordered queue — the exact "topics stored and never queued" problem re-created one layer up, now with a misleading "posição N de M" message.
- Suggested mitigation: Define a backlog cap/expiry policy and the FIFO-vs-requeue rule (e.g. fixed delay re-attempt at head, or documented priority exception) before P2 ships the Telegram position/ETA promises.
- Open question for author: At cap 1 and 3 topics/day, what is the intended steady-state backlog size, and who trims it?

### [INFO] SSE relay via NOTIFY is lossy, `worker_last_seen` is unspecified, and the web/worker step split is deferred to ticket time
- Assumption: Postgres NOTIFY (in-process hub confirmed at workflow_sse_hub.py:20-82) is an adequate cross-process transport; the web relays.
- Risk: NOTIFY is fire-and-forget: during a web restart or momentary LISTEN gap, progress events are dropped and SSE clients silently stall until the next phase boundary. `worker_last_seen` has no specified mechanism (table? pgq statistics?). And "which light steps stay in the web lifespan … decided in the ticket" defers a core architecture boundary (two schedulers, split ownership of reapers/notices) to implementation time — the kind of decision that should be in this ADR.
- Impact: Stale dashboards during the exact incidents the plan targets; risk of steps being duplicated or orphaned across the two processes.
- Suggested mitigation: Specify event re-fetch on SSE (re)connect (state query, not just stream), name the `worker_last_seen` storage, and put the step-ownership matrix in the plan rather than the ticket.
- Open question for author: How does an SSE client that reconnects mid-phase learn current phase without the missed NOTIFY events?

### [WARN] The memory arithmetic does not close — the worker adds demand to an exhausted box, and the decision-dominating variable (HD export) is still open
- Assumption: A worker capped at ≤900m (1400m possible) with `memswap_limit = mem_limit` fits on the droplet once P5 caps the web tier, and a disposable-droplet load test proves "no container may be OOM-killed".
- Risk: Caps don't create headroom — they only convert kernel OOM into per-container OOM. Verified current caps: clickhouse 1536M (docker-compose.prod.yml:249-253), langfuse-worker 768M (:384-387), minio 256M (:274-277), opencode 1g (:163), plus *uncapped* backend/langfuse/frontend/postgres on a 3.8 GB box the packet itself says has ~860 MB available and ~190 % committed. The plan's own §8 admits "Chromium HD export may exceed 1.4 GB on some carousels" — above both the 900m target *and* the physically free memory. The one-shot load test can pass on N carousels and fail on carousel N+1 (HD memory is content-dependent).
- Impact: Worker OOM-kill loops mid-Chromium. Worse, the designed response is self-defeating: an OOM is deterministic, so "Tentar de novo" (retry with attempts reset) re-runs the same run into the same ceiling — an infinite manual loop for Pedro ending in dead_letter every 4 attempts. Alternatively the kernel OOM killer moves to postgres/web — the exact incident class the ADR exists to prevent.
- Suggested mitigation: Make the HD decision *before* ADR acceptance, not inside P0; publish the box-level RSS budget equation (Σ caps + uncapped RSS + worker peak vs 3.8 GB) as an ADR precondition; classify OOM/cgroup-kill errors as non-retryable in the error table; put the biggest lever on the table — the ~3.3 GB Langfuse/ClickHouse/minio observability stack was never considered as headroom source in the options analysis.
- Open question for author: With HD dropped and measured run RSS in hand, does the equation actually close without shrinking the observability stack — and if not, why is the queue the right spend of the box's last 900 MB?

### [WARN] Rollback strands every active run: the flag-off story is internally contradictory
- Assumption: §7 rollback — "flag off (web resumes in-process execution) … queued autopilot runs are replayed by the in-process runner's existing `queued` selection".
- Risk: The same §7 specifies "the in-process runner skips any autopilot run that has an active (`queued`/`running`/`retry_wait`) `generation_runs` row". Both statements cannot hold: on flag-off, every run with an active `generation_runs` row is skipped by the web runner *and* ignored by the dry-run worker dispatcher. The dispatcher's skip rule also keys on "no `generation_runs` row", so the daily scan's re-enqueue is off too.
- Impact: Turning the flag off mid-queue (the primary rollback lever, and the documented chaos scenario) strands all queued/in-flight runs until the flag is re-enabled — rollback of a broken queue becomes a partial outage of generation itself. Over-cap backlog behavior under flag-off (a P2 feature layered on top) is unspecified.
- Suggested mitigation: Define the flag-off transition as an explicit migration step: CAS all active `generation_runs` rows to `cancelled` (handing the autopilot run back to `queued`) before the web path resumes ownership; add it to the "queue off and on mid-run" Gherkin scenario.
- Open question for author: On flag-off, what terminal state does an *in-flight* job get, and who then drives the half-generated carousel — and why is that not spelled out in §7?

### [WARN] Dual-driver race at flag transitions is fenced on only one side (TOCTOU)
- Assumption: "One owner per run at any time" is achieved by heuristic skip checks: the worker takes `pg_try_advisory_xact_lock(project)` (§4.3), but nothing makes the *web* in-process path (flag-off runner, `asyncio.create_task` resumes — verified fire-and-forget at `application/services/carousel/editorial_workflow_resume_runner.py:106-116`) acquire the same lock. Cross-path exclusion is "dispatcher checks `phase_status='in_progress'` + heartbeat + no `generation_runs` row at T0".
- Risk: Dispatcher checks at T0, web claims at T1, worker dequeues at T2 → two drivers on one carousel. The `run_epoch` fence + heartbeat (verified real: `carousel_run_guard.py`, `carousel_run_reaper.py:163-186`) is the backstop, but a fence violation is precisely what produces today's `escalated / run_stale` human-parked runs — the failure mode this ADR exists to eliminate.
- Impact: Rare but consequential: a duplicate-driver window during every flag flip and every deploy straddling the transition; worst case is a fenced zombie that parks a run Pedro must manually recover — via the queue UI that the flag just disabled.
- Suggested mitigation: Make claim ownership a single primitive both paths must pass through (same advisory lock, or the `generation_runs` row-insert CAS) instead of observational skip rules; test the race deterministically (both paths attempting claim concurrently) in the integration suite, not just the sequential double-tap case.
- Open question for author: Why is the advisory lock worker-only when the stated invariant is cross-process?

### [WARN] Schema-delivery story for `generation_runs` is self-contradictory and the "Alembic migration" is operationally decorative
- Assumption: §4.2 says the table is "new table → created by `create_all`, no ALTER"; the ADR guards and §8 say it "ships as an Alembic migration plus the deploy one-shot, **not** via `create_all`". Both are in the same packet.
- Risk: Operationally, Alembic cannot run in prod: migrate-on-deploy is disabled after the 2026-06-18 outage, prod was never stamped, and re-enabling requires the documented one-time `alembic stamp` reconcile (`.github/workflows/deploy.yml:255-262`) — which appears in no phase of this plan. So the real mechanism is another bespoke DDL one-shot (the palette pattern), and the ORM metadata + Alembic file + one-shot DDL become three drift-prone sources — the exact AE-0207 class that already silently 500'd prod three times (`deploy.yml:237-245`; the repo even keeps `infrastructure/database/schema_drift.py` as a scar-tissue gate). Also, an Accepted ADR-012 is being "amended in practice" by a Proposed ADR — governance-wise that is a supersede, not an amendment.
- Impact: If the packet can't agree with itself on how its one core table reaches prod, the P1 ticket will pick one arbitrarily; whichever loses drifts.
- Suggested mitigation: Pick one mechanism (the one-shot), generate/validate the Alembic file against it via the existing schema-drift gate in CI, and fold the alembic-chain reconcile (incl. the stale two-heads comment in deploy.yml) into the plan or drop the Alembic claim.
- Open question for author: Which of the two statements is wrong, §4.2 or §8 — and who runs `alembic stamp` on prod, in which phase?

### [WARN] The plan automates recovery from a failure whose root cause is unconfirmed
- Assumption: "10-21 and 10-22 each had one `escalated / run_stale` from that batch (cause unconfirmed)" — yet recurring stale runs are the motivating evidence for the queue, retry, lease and dead-letter machinery.
- Risk: If `run_stale` stems from provider slowness beyond lease timeouts, the queue converts it into retry storms/dead letters, not success; if it stems from a heartbeat/stepping bug, the worker inherits it (heartbeats and stepping are now per-process, on a CPU-contended 2-vCPU box where `to_thread` PIL work runs next to Chromium). The design's timing constants (heartbeat 300s, drain 300s, resume ≤6 min, reasoning-model timeout 240s + fallback 120s) are asserted, never derived — they nearly sum to their own budget with no slack.
- Impact: The system ships perfectly and the original symptom persists, now wrapped in queue state.
- Suggested mitigation: Root-cause the two October escalations (reaper logs, traces, provider latency) as a P0 exit criterion; derive heartbeat/drain/resume budgets from measured phase durations instead of round numbers.
- Open question for author: What does the reaper/trace evidence say those two runs died of?

### [INFO] The idempotency audit that at-least-once safety depends on is deferred into P1 with no inventory
- Assumption: "any non-idempotent side effect inside a node (e.g. a Telegram send not via outbox) would repeat on lease expiry — audit nodes in P1 (list them in the ticket)".
- Risk: The plan's duplicate-safety story rests on an audit that hasn't happened; side-effect + checkpoint-write is inherently non-atomic, so node replay after a crash between the two repeats the effect. The chaos test ("no duplicate Telegram messages / artifacts") exercises one path, not every node.
- Impact: A single unaudited direct Telegram/Instagram/Pinecone write inside a node becomes a user-visible duplicate under the new *more frequent* requeue conditions (heartbeat expiry now triggers requeue where today the run just parks).
- Suggested mitigation: Do the side-effect inventory now, as plan-time evidence, not P1 ticket work; make "all external writes outboxed or CAS-claimed" a merge gate for P1.
- Open question for author: How many nodes make external calls today, and how many are already outboxed?

### [INFO] The outbox + daily-scan design neutralizes the ADR's stated reason for rejecting Redis queues, and much of the "so we don't build it" value of PgQueuer
- Assumption: Option 4 was rejected partly because Redis would be "a second source of truth (RDB/AOF loss windows)". But under this design the queue is *not* a source of truth (`generation_runs` is), and the daily scan re-enqueues "queued rows with no active job" — i.e., the architecture already tolerates a lossy queue and self-heals within 24 h.
- Risk: The differentiator for PgQueuer shrinks to dequeue/heartbeat/requeue primitives — while the plan builds, around it: its own runs table, dispatcher, attempt counter, dead-letter mirror, jitter, purge, and a 6-item semantics gate with an escape hatch to option 1. That is most of option 1's code plus a third-party schema in the prod DB and an install/upgrade one-shot to own forever. The choice may still be right (ops CLI, maintenance), but the Consequences section understates retained complexity, and the semantics gate omits two load-bearing assumptions: `@schedule` run-once-per-day dedupe across workers (§4.6) and the log-purge API the 30-day cleanup uses.
- Impact: If any ungated semantic (especially schedules dedupe) mismatches, discovery happens in prod at 04:00 BRT.
- Suggested mitigation: Add schedule-dedupe and purge semantics to the gate matrix; state honestly in the ADR that the in-house fallback is ~the same surface minus three primitives.
- Open question for author: What is the measured delta between "wrap PgQueuer" and "own the table", in lines and in gates?

### [INFO] Dev/prod checkpointer parity silently undermines the resume tests
- Assumption: "resumes from the checkpoint" — but compose defaults `CAROUSEL_CHECKPOINT_BACKEND` to `memory` (docker-compose.prod.yml:82); only the deploy-written `.env` sets postgres (`deploy.yml:158`).
- Risk: Any environment brought up without the deploy `.env` (CI integration tests, a disposable droplet assembled by hand) has no durable checkpoints, so "killed worker resumes from checkpoint" tests would validate a no-op resume path and pass vacuously.
- Impact: False green on the plan's central chaos criterion.
- Suggested mitigation: Make the chaos/integration suite assert `CAROUSEL_CHECKPOINT_BACKEND == postgres` at startup; document the droplet bring-up as restore-including-`.env`.
- Open question for author: How is the disposable droplet's `.env` guaranteed to match prod's?

### [INFO] New privileged worker container: resource caps specified, security caps not
- Assumption: The worker is "same image" — inheriting every secret (IG tokens, Telegram tokens, LLM keys) with full default capabilities, and PgQueuer's tables live in the app DB where any SQL injection can mass-delete/requeue/poison jobs; new `POST /api/generation-runs/{id}/retry|cancel` endpoints and the cap-bypassing "Gerar agora" are additional auth surface (owner/admin stated, untested in the packet).
- Risk: The repo already hardened a less-trusted sidecar (`opencode`: `cap_drop: ALL`, `no-new-privileges`, read-only root — docker-compose.prod.yml:150-164); the plan's worker gets `mem_limit`/`cpus` but none of that.
- Impact: Low for a single-operator product, but the worker is now the component that executes arbitrary graph side effects unattended.
- Suggested mitigation: Apply the sidecar hardening baseline to the worker container in P1; add an auth test for the new endpoints including the cap bypass.
- Open question for author: Is there a reason the worker needs more capabilities than the sidecar?

## Findings

### [BLOCKER] Validation environment as specified can fire real production side effects
- Assumption: a disposable droplet "restored from a prod backup INCLUDING the deploy-written `.env`" is a safe staging stand-in (§4.4, §6).
- Risk: the deploy-written `.env` holds live secrets (`deploy.yml:190-225`: Telegram bot/alerts tokens, `META_IG_ACCESS_TOKEN`, Pinecone, LLM keys). A restored stack with `AUTOPILOT_ENABLED`/publish steps and real tokens can post to the **real Instagram account**, send **real Telegram messages**, and spend real API budget during chaos/load tests. Publish claims are per-database (`modules/autopilot/infrastructure/publish_claims.py`), so the copy's claims do not fence the real account.
- Impact: the validation itself becomes an outage/abuse event; the chaos criterion "no duplicate Telegram messages" is measured on a box wired to the real bot.
- Suggested mitigation: make credential scrubbing/stubbing (Telegram, Meta, Pinecone, GrokBot webhook, LLM endpoints) a mandatory, tested step of the droplet build; keep prod data but never prod outbound credentials.
- Open question for author: which external endpoints does the restored droplet actually reach, and what blocks the 04:00 scan / publish tick on it from touching production?

### [WARN] The ADR records a decision before its own exit criteria; the memory budget is the unresolved load-bearing wall
- Assumption: P0 measurements, the box memory budget, and `run_stale` root cause will confirm the design (§Validation, P0 exit criteria 1-3) — yet "Chosen option (Pedro, 2026-10-22)" is already recorded in the ADR.
- Risk: the box shows ~860 MB free / ~190 % committed; the observability stack alone carries ≈3.5 GB of limits today (`docker-compose.prod.yml`: clickhouse 1536M, langfuse-worker 768M, minio 256M, opencode 1g) plus uncapped langfuse/postgres/backend/frontend. The worker adds 150-300 MB idle and Chromium peaks possibly ~1.4 GB; with `memswap_limit = mem_limit`, an over-budget export becomes a deterministic cgroup OOM-kill → heartbeat requeue → attempts → dead letter. A carousel that legitimately needs more than the cap becomes unproducible, not just slow.
- Impact: false-positive dead letters; or the plan stalls ("queue waits for a bigger droplet") after the org has already emotionally accepted ADR-0026. Also, P5's caps on the currently-uncapped web tier carry their own rollback-untested outage risk.
- Suggested mitigation: reword the ADR to "accepted-provisional on P0 criteria 1-3"; define a worker-escape valve (skip-HD → on-demand render) as part of P1, not a contingency; add a P5 rollback plan (cap values + how to revert without an outage).
- Open question for author: what is the measured backend RSS today, and what cap would it survive — i.e., what is P5's own blast radius?

### [WARN] dead_letter mirroring has no owner: the handler is gone by the time PgQueuer "holds" the job
- Assumption: "our handler mirrors the state into `generation_runs.status='dead_letter'`" (§4.3).
- Risk: `on_failure="hold"` happens inside PgQueuer after the handler raises/retries exhaust; at that moment no handler code runs. If no component polls held jobs, the mirror — and with it the Telegram Retry/Discard message, the dashboard panel, and the CAS-on-`dead_letter` retry — is never written. The 04:00 scan (§4.6 step 3) only *re-enqueues* transient-class dead letters; it is not specified as the mirror writer, and a 20-hour visibility gap for a failed morning run is realistic.
- Impact: the headline UX ("Pedro sees failures and can retry") silently depends on an unspecified reconciler.
- Suggested mitigation: make the 10 s dispatcher the reconciler: `SELECT … FROM pgqueuer WHERE status='failed'/held` → mirror + notify; state its SLA and test it.
- Open question for author: exactly which code path writes `dead_letter` and sends the Telegram message when retries exhaust — name the component and the trigger?

### [WARN] Attempt accounting conflates run-level budgets with checkpoint-resume progress, and double-counts with PgQueuer
- Assumption: `attempts` incremented at job start, `max_attempts=4` per run (§4.2-4.3), plus PgQueuer's own `max_attempts` 4 on the job.
- Risk: two counters bound the same job, and the run-level budget contradicts resume semantics: a long carousel whose phases each succeed once but which hits 4 transient failures across *different* nodes (each retry making real forward progress from the checkpoint) dead-letters as "poison". Heartbeat-requeues (e.g. two deploys in one day) consume the same budget.
- Impact: chronic false dead letters on exactly the long HD/export runs the plan worries about; Pedro's "Tentar de novo" resets attempts, so the failure mode is nagware rather than protection.
- Suggested mitigation: budget attempts per (run, step/node) keyed like the idempotency keys, with a higher or progress-aware run ceiling; document which counter wins when they disagree.
- Open question for author: how many nodes/phases does one carousel run have, and what fraction of historical failures were "no progress" vs "progressed then failed"?

### [WARN] Hardened worker container vs Chromium sandbox: exports may dead-letter on day one
- Assumption: `cap_drop: [ALL]`, `no-new-privileges`, read-only rootfs, tmpfs shm are compatible with headless Chromium (§4.4).
- Risk: today Chromium launches with default args (`p.chromium.launch()`, `infrastructure/external/playwright_export.py:308`) in an *uncapped, unprivileged-default* container. Under `cap_drop ALL` + `no-new-privileges`, Chromium's sandbox generally needs a seccomp profile permitting user namespaces or `--no-sandbox`. The plan lists `--disable-dev-shm-usage`/`--renderer-process-limit` but no sandbox decision.
- Impact: every export fails in the hardened worker — a full P1 rollout blocker discovered at integration time.
- Suggested mitigation: add a P1 entry criterion: export runs under the exact hardened compose config, with the sandbox choice (custom seccomp vs `--no-sandbox` + compensating controls) documented as an accepted trade-off.
- Open question for author: has anyone run this Playwright build under `cap_drop ALL` on this Docker/kernel version?

### [WARN] Three sources of DDL truth; the drift gate doesn't check the one that runs in prod
- Assumption: one-shot raw SQL ≡ Alembic file ≡ ORM `create_all`, "no drift" (§8 Schema governance).
- Risk: prod's authoritative DDL becomes the one-shot's raw SQL; the existing schema-drift gate compares ORM vs Alembic (`infrastructure/database/schema_drift.py`), not raw SQL. A divergence (default, partial-index predicate, nullability) manifests only in prod. Two extra subtleties: `ON CONFLICT (dedupe_key) DO NOTHING` must repeat the partial-unique-index predicate to bind to it; and `pgq upgrade` is third-party DDL whose lock behavior is assumed "never blocks" by analogy with palette_timestamptz (`deploy.yml:288-300`) — a script the project controls, which `pgq` is not.
- Impact: silent prod-only schema drift in a system whose last drift incidents were prod 500s (`deploy.yml:237-239`).
- Suggested mitigation: generate the one-shot's `generation_runs` DDL from the Alembic file (single source), add a CI assert that one-shot SQL == rendered Alembic DDL, and integration-test the ON CONFLICT predicate against the partial index.
- Open question for author: is `pgq install/upgrade` transactional on failure mid-way, and has its lock footprint been observed on the live DB?

### [WARN] A destructive bugfix (checkpoint pruning) is piggybacked on the daily scan ticket
- Assumption: the 04:00 scan deletes checkpoints "for published/rejected projects (fixes AE-0342's never-matching prefix)" (§4.6 step 4).
- Risk: deleting checkpoint rows using a matcher that has *never worked correctly*, against a 1.4 GB table, inside a queue-recovery ticket. A wrong matcher destroys resume state for projects that later need republish/rework.
- Impact: unrecoverable runs — the exact class of loss this ADR exists to prevent.
- Suggested mitigation: split into its own ticket: dry-run count, owner sign-off on the matched set, backup, then delete.
- Open question for author: what was the actual root cause of the never-matching prefix, and is the fix tested against real prod data?

### [INFO] The motivating incident is unexplained; budgets are round numbers until it is
- Assumption: heartbeat 300 s / lease / 6-min resume targets are safe (§4.3, §Validation).
- Risk: the 10-21 and 10-22 `run_stale` escalations that motivate the whole redesign are cause-unknown (the plan admits this). If the cause is shared-resource saturation (DB pool, event loop, provider latency), the worker inherits it — it adds a new 3+2 connection pool and NOTIFY traffic to the same Postgres.
- Impact: the new machinery may faithfully reproduce the old failure.
- Suggested mitigation: keep P0 exit #3 as a hard gate before P1 *merge*, not just before enable.
- Open question for author: what is the current `max_connections` headroom on prod Postgres once web (5+10) + worker (3+2) + Langfuse + one-shots coexist?

### [INFO] Advisory-lock pinning under a pooled connection is an unstated correctness detail
- Assumption: `pg_try_advisory_lock(project)` held "for the whole time it drives a phase" on both paths (§7).
- Risk: session-level advisory locks live on one connection; with a 3+2 pool, a recycle/checkout change mid-phase silently drops the lock, re-opening the two-drivers race the lock exists to close.
- Suggested mitigation: dedicate a pinned connection (or use xact-scoped locks at claim boundaries) and add a determinism test for connection recycle mid-phase.
- Open question for author: which pool object holds the lock, and what happens on disconnect mid-phase?
