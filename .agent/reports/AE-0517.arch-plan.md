# Architecture Plan: AE-0517 — Carousel generation queue, dead letter and daily recovery

**Date:** 2026-10-22
**Status:** Plan (ADR-0026 proposed)
**Mode:** architect-skill plan mode
**Tier:** T3 (concurrency, failure recovery, new runtime component)

## 1. Goal

Pedro can approve several themes on the same day and they are generated one after another (bounded concurrency),
in order, without blocking each other, without slowing the website, and without getting lost on deploys or crashes.
Transient failures retry automatically; runs that keep failing land in a visible dead-letter state with the reason;
a daily scan recovers stuck work. No new paid service, no heavy infrastructure.

## 2. Findings that shape the design (evidence)

Current execution model (origin/main 23208e4f4):

- Topics arrive from the external Grok Bot at 08:00 BRT (`ops/grokbot/grok-bot/v3/routine.md`) via
  `POST /api/autopilot/topics` → `TopicIntakeService.accept` (`modules/autopilot/application/topic_intake.py:126`) →
  `autopilot_runs(state='queued')`. The daily cap is enforced only at intake; over-cap topics are stored and never
  queued (`domain/intake.py:254-266`).
- Pedro's Telegram approval per theme is the POV-thesis prompt (`application/thesis_prompts.py:74-110`): Confirmar
  moves `awaiting_thesis → queued` (CAS) but does not start anything. All prompts of the morning batch arrive together.
- The runner (`modules/autopilot/application/runner.py:162-232`) runs inside the 60 s in-process worker loop
  (`application/workers/workflow_workers.py:221-272`, started from the uvicorn lifespan, `bootstrap/app_factory.py:156`).
  `RUNS_PER_TICK=1` and `_first_run` (generating → reworking → queued) serialize autopilot runs by accident, and each
  phase is awaited inline, blocking reapers, publish and notices.
- Interactive resumes: `asyncio.create_task` in the web process, no global limit
  (`editorial_workflow_resume_runner.py:75,106-116`).
- Deploy = `docker compose down/up` (`.github/workflows/deploy.yml:230-234`), no grace period; lifespan shutdown does not
  drain carousel tasks; reaper (`infrastructure/database/carousel_run_reaper.py:89-224`) parks orphans for a human;
  no automatic re-run.
- LangGraph checkpointer: AsyncPostgresSaver in prod (deploy writes CHECKPOINTER=postgres), thread id = project id;
  re-driving replays only the interrupted node. Checkpoint pruning is broken (AE-0342, DB reached 1.4 GB).
- Prod applies schema with `Base.metadata.create_all` (new tables are created, new columns are not); alembic does not
  run on deploy.

Capacity (prod, 2026-10-22, read-only):

- 2 vCPU / 3.8 GB RAM, ~860 MB available, 2 GB swap ~35-47 % used, committed memory ~190 % all week; no OOM kills in
  30 days. backend, langfuse (762 MB), frontend, postgres have no memory limit; nothing has CPU shares.
- backend = one uvicorn process, one event loop. Heavy local steps: 4 headless Chromium launches per carousel
  (`infrastructure/external/playwright_export.py:308`, HD at deviceScaleFactor 2, 2800×3600), synchronous PIL
  re-saves (`_crop_border_artifact`) and img2pdf (`PdfSlideBuilder.build`) on the event loop.
- Daily batch: 3 runs created ~11:04-11:12 UTC; 10-21 and 10-22 each had one `escalated / run_stale` from that batch
  (cause unconfirmed).

Options research (sources in ADR-0026 discussion; summary): Postgres-native queues fit best (no new service,
transactional enqueue). PgQueuer is the strongest library; arq is maintenance-only; Celery has no native async;
LangGraph Agent Server needs a paid license. External free tiers (GitHub Actions cron, QStash, Cloudflare Queues) are
acceptable only as triggers, never as the queue (content must not leave the box).

## 3. ADR check

Required: yes. `docs/decisions/0026-carousel-generation-queue.md` (status proposed). Decision (Pedro, 2026-10-22):
**PgQueuer** (MIT, asyncpg-native Postgres queue) as the job engine, consumed by a separate resource-capped worker
container; our own `generation_runs` table stays the source of truth for the dashboard, Telegram and idempotency. The
AE-0017 recovery plan explicitly requires an ADR before any new queue mechanism.

## 4. Target design

### 4.1 Components

```
Grok Bot ──► /api/autopilot/topics ──► autopilot_runs(queued)
Telegram (Confirmar thesis / Aprovar) ──► CAS + generation_runs row + PgQueuer enqueue   ┐ web: backend (uvicorn)
Dashboard (Start / Resume / Retry)    ──► generation_runs row + PgQueuer enqueue (202)   ┘ never runs a graph phase
PgQueuer tables (Postgres) ◄── generation-worker (same image, cmd `pgq run rag_backend.worker.main:create_pgqueuer`)
                                 ├─ entrypoints: autopilot_start, autopilot_step, workflow_resume, workflow_start
                                 ├─ one LangGraph phase per job (resume from checkpoint), concurrency_limit=1
                                 ├─ PgQueuer retries (backoff), on_failure="hold" = dead letter, heartbeat requeue
                                 ├─ global export lock = 1 (Chromium)
                                 └─ @schedule("0 7 * * *") daily recovery scan (= 04:00 BRT) + light periodic steps
```

### 4.2 Data model

PgQueuer owns its own tables (`pgqueuer`, `pgqueuer_log`, `pgqueuer_statistics`, `pgqueuer_schedules`; exact names per
the pinned version). Prod does not run migrations, so they are installed by an idempotent **deploy one-shot**
(`pgq install` on first deploy, `pgq upgrade` afterwards — it applies only missing pieces) in deploy.yml right after the
blog cutover step, using the palette_timestamptz pattern: never blocks the stack, fails the job at the end on error. The
PgQueuer version is pinned in `backend/pyproject.toml` / `uv.lock`; upgrades are their own PR.

Our own table `generation_runs` (delivered by the deploy one-shot, see §8 "Schema governance") — what Pedro sees and what Telegram
and the autopilot state machine reference:

| column | type | notes |
|---|---|---|
| id | uuid pk | also the LangGraph-independent run id |
| kind | varchar(32) | `autopilot_start`, `autopilot_step`, `workflow_resume`, `workflow_start` |
| carousel_project_id / autopilot_run_id | uuid null | FKs |
| dedupe_key | varchar(160) | partial UNIQUE where status in (queued, running, retry_wait); also passed to PgQueuer as `dedupe_key` |
| pgq_job_id | bigint null | current PgQueuer job id (changes on retry/requeue) |
| payload | jsonb | typed per kind (Pydantic) |
| status | varchar(16) | `queued`, `running`, `retry_wait`, `succeeded`, `dead_letter`, `cancelled` |
| attempts / max_attempts | smallint | **our own counter**, incremented at job start (poison guard, see 4.3); default max 4 |
| next_attempt_at | timestamptz null | shown in the dashboard while `retry_wait` |
| last_error_code / last_error | varchar / text | classified error (no secrets, truncated) |
| created_at / started_at / finished_at / updated_at | timestamptz | |

Indexes: `(status, created_at)`; partial unique `(dedupe_key)`; `(carousel_project_id)`; `(autopilot_run_id)`. Also the
missing index on `carousel_projects(phase_status, current_phase)` (index on an existing table → same deploy one-shot,
`CREATE INDEX CONCURRENTLY IF NOT EXISTS`).

### 4.3 Claim, lease, retry, dead letter (PgQueuer + our guards)

- Enqueue (as built): the dashboard resume route writes ONLY our `generation_runs` row (`status='queued'`,
  `pgq_job_id NULL`, `ON CONFLICT (dedupe_key) DO NOTHING`) in the same transaction as its CAS, a transactional outbox.
  The Telegram callback writes no queue row: the autopilot run's own CAS on `autopilot_runs` is the durable record, and
  the dispatcher stages one `generation_runs` row per active autopilot run on its next 10 s poll (§9). Neither touches
  PgQueuer's tables, so a missing/broken PgQueuer install can never roll back an approval. A **dispatcher** (worker, every 10 s, plus the 04:00 scan) hands `queued` rows without `pgq_job_id` to
  PgQueuer (`enqueue`, then stores the job id; idempotent: a crash between the two is resolved by looking up the job by
  `dedupe_key` before enqueueing again). This removes the dependency on PgQueuer accepting an external transaction.
- Claim and concurrency: PgQueuer dequeues with `FOR UPDATE SKIP LOCKED` in FIFO order (strict FIFO, Pedro's decision);
  `concurrency_limit=1` per entrypoint group, enforced in the database across workers (`GENERATION_WORKER_CONCURRENCY`,
  default 1). Per-project exclusivity: the job handler takes `pg_try_advisory_xact_lock(project)`; if another run holds
  it, the job is re-enqueued with a short delay (never two jobs driving one carousel).
- Heartbeat: PgQueuer heartbeats from the worker's event loop; set `heartbeat_timeout` to 300 s (not the 30 s default)
  and run CPU-heavy steps (`_crop_border_artifact`, `PdfSlideBuilder.build`, PIL validation) in `asyncio.to_thread` so
  heartbeats are never starved (a starved heartbeat makes PgQueuer re-queue a live job → duplicate run).
- Retries: PgQueuer's retry executor (`DatabaseRetryEntrypointExecutor`): `max_attempts` 4, `initial_delay` 30 s,
  `backoff_multiplier` 2, `max_delay` 30 min; jitter ±20 % added by our handler (PgQueuer's docs do not document jitter).
  Only transient errors are retried (reuse `StartStatus.PROVIDER_OUTAGE`, model-breaker errors, HTTP 429/5xx/timeouts);
  permanent errors (validation, content-gate escalation, missing project) raise a non-retryable error → dead letter now.
- Dead letter: `on_failure="hold"` keeps failed jobs in PgQueuer as `failed`. Permanent errors are mirrored by our handler
  (it marks `generation_runs.status='dead_letter'` before raising). For jobs PgQueuer holds after exhausting retries — when
  no handler code runs — the **dispatcher is the reconciler** (round-3 review): every 10 s it selects held/failed PgQueuer
  jobs not yet mirrored, writes `generation_runs.status='dead_letter'` with the last classified error, and stages the
  Telegram notice through the outbox (SLA ≤ 1 min; integration test: exhaust retries → mirrored + one notice); the autopilot run goes to `escalated`/`failed`
  exactly as today (CAS + outbox), so Telegram notices keep working. Retry from Telegram/dashboard = PgQueuer `requeue`
  + our row back to `queued` with attempts reset (CAS on `dead_letter`).
- **Attempt budgets (round-3 review)**: our counters are authoritative; PgQueuer's own `max_attempts` is set high (20) and
  only acts as transport. We budget per **(run, phase)** — keyed like the idempotency keys — with at most 3 attempts per
  phase, plus a run-level ceiling of 10 attempts that only counts attempts which made **no** checkpoint progress. A run
  that keeps advancing phase by phase is never dead-lettered as poison; a run stuck on the same phase (or crash-looping
  with no progress, e.g. stale-heartbeat requeues) is. The handler increments the counter first thing and dead-letters
  without running the graph when a budget is exceeded. "Tentar de novo" resets only the failing phase's counter.
- Worker death (OOM, deploy): PgQueuer re-queues the job after the heartbeat timeout; LangGraph resumes the interrupted
  node from the checkpoint; the existing `run_epoch` fence + heartbeat columns on `carousel_projects` keep stale writers
  out. External side effects stay keyed/CAS-guarded: image bridge jobs (token), Instagram publish (claim), Telegram
  notices (outbox cursor), export writes by artifact version.

### 4.4 The worker

- New module `rag_backend/worker/main.py` exposing `create_pgqueuer()` (same image; command
  `pgq run rag_backend.worker.main:create_pgqueuer`). It builds the DI container like the app factory but starts no HTTP
  server, registers the entrypoints (`autopilot_start`, `autopilot_step`, `workflow_resume`, `workflow_start`) and the
  daily schedule. `concurrency_limit` = `GENERATION_WORKER_CONCURRENCY` (Pedro: 1). Graceful shutdown: PgQueuer stops
  dequeuing on SIGTERM; the current phase gets `stop_grace_period` (120 s); an unfinished job is re-queued by heartbeat
  timeout and resumes from the checkpoint (our attempt counter treats it as an attempt only if it actually started).
- Move the heavy loop steps out of the web process: autopilot runner stepping, rework step, recovery and the daily
  scan run in the worker. The web lifespan keeps only light, fast periodic steps (scheduled blog publish, reminders,
  notices) or they move too — implementation detail decided in the ticket, with the rule: nothing that awaits an LLM or
  Chromium runs in the web process.
- Global export semaphore (cross-process): a Postgres advisory lock `pg_try_advisory_lock(EXPORT_LOCK_KEY)` around
  `export_slides`, plus run PT/EN and standard/HD exports sequentially; Chromium flags `--disable-dev-shm-usage`,
  `--renderer-process-limit=1`. Move `_crop_border_artifact` and `PdfSlideBuilder.build` to `asyncio.to_thread`.
- Container limits (docker-compose.prod.yml): `mem_limit` = measured worker peak + 15 %, and never more than the measured
  free headroom AFTER the web tier is capped. P5 measured a prod run peak of 1222 MiB (one HD export), so the worker
  is capped at 1600m; the backend keeps 1600M while it still renders dashboard exports, finalize and refinement in
  process, and the cross-process export slot keeps one Chromium export on the box at a time (budget with Langfuse off
  the box in `.agent/reports/AE-0522.memory-budget.md`),
  `memswap_limit` = `mem_limit` (no swap for the worker),
  `cpus: 1.0`, `cpu_shares: 256` (web services keep the default 1024 so visitors win contention), `shm_size: 256m`,
  `stop_grace_period: 120s`, `restart: unless-stopped`. Add reservations/limits to backend/frontend (and cap langfuse)
  in a separate infra ticket, measured first.
- DB pool for the worker: 3 connections (+ overflow 2), so the web pool (5+10) is not starved.
- Chromium under hardening (round-3 review): P1 entry criterion — a full export runs green under the EXACT hardened
  compose config before the PR merges. Chromium's sandbox needs user namespaces that `cap_drop: ALL` +
  `no-new-privileges` remove, so the accepted trade-off is `--no-sandbox` with compensating controls (non-root user,
  dropped capabilities, read-only root, egress limited by the app's own endpoints, only trusted first-party HTML is
  rendered), documented in the ticket; a custom seccomp profile is the alternative if the test shows it works.
- Security baseline (round-2 review), same as the hardened `opencode` sidecar: `cap_drop: [ALL]`,
  `security_opt: [no-new-privileges:true]`, read-only root filesystem with tmpfs for /tmp and Chromium's profile/shm, only
  the env vars the worker needs (no web-only secrets), no published ports. New endpoints
  (`/api/generation-runs/*`, "Gerar agora") get owner/admin auth tests including the cap bypass.
- Advisory lock pinning (round-3 review): the per-project lock is a session lock held on a DEDICATED connection checked
  out for the whole drive (never returned to the pool mid-phase); losing that connection aborts the drive and releases
  ownership cleanly; test: connection drop mid-phase → no second driver, run resumes after the lease.
- Checkpointer parity: the worker refuses to start unless `CAROUSEL_CHECKPOINT_BACKEND=postgres` (compose defaults it to
  `memory`, docker-compose.prod.yml:82); integration and chaos suites assert the same, and the disposable test droplet is
  built from a prod backup INCLUDING the deploy-written `.env`.

### 4.5 Telegram and the "approve several themes" flow

- Each thesis prompt keeps its Confirmar/Editar/Descartar buttons; Confirmar now also enqueues
  `autopilot_start` (dedupe `run:<id>:start`) and edits the message to show **"Na fila: posição N de M — início
  estimado HH:MM"** (position from the queue order, estimate from the moving average of recent job durations).
- New button on the morning batch summary: **"Aprovar todas"** confirms every pending thesis of the batch in one tap
  (each with its own CAS + enqueue).
- Over-cap topics (Pedro's decision): instead of being dropped, they are stored as a backlog with a `not_before` date
  (next day's slot) and appear in the next morning's prompts. They are also listed in the dashboard queue panel, where
  Pedro can trigger any of them manually ("Gerar agora": enqueue now, outside the daily cap). The daily cap keeps its
  meaning (max automatic generations started per day).
- When a job reaches `dead_letter`, Pedro gets one Telegram message with the reason and buttons **"Tentar de novo"**
  (re-enqueue with attempts reset, CAS on dead_letter) and **"Descartar"** — this also fixes AE-0410 (escalated runs
  could not be resumed from Telegram) for queue-originated failures.

### 4.6 Daily recovery scan (04:00 BRT = PgQueuer `@schedule("0 7 * * *")` in UTC; PgQueuer's schedules table makes it
run once per day across workers)

1. Approved/queued autopilot runs with no active job → enqueue (`autopilot_start`/`autopilot_step`).
2. `carousel_projects` in `phase_status='in_progress'` whose heartbeat is older than the lease and no running job →
   enqueue `workflow_resume` (replaces "park and wait for a human" for autopilot runs; interactive runs stay parked
   and are listed for Pedro).
3. `dead_letter` runs (PgQueuer `failed`, held) younger than 7 days whose error was transient-class (e.g. provider outage that lasted hours) →
   re-enqueue once (`recovery_attempt` flag) — never loops.
4. Expire/purge: `succeeded` `generation_runs` and PgQueuer log rows older than 30 days deleted. Checkpoint pruning is
   NOT part of this scan (round-3 review): it is its own ticket (AE-0342 fix) with a dry-run count, Pedro's sign-off on
   the matched set, a backup, then the delete.
5. Summary to Pedro (Telegram, one message): recovered N, still dead M, queue length K.
Optional external trigger (free): none needed; the worker owns the schedule. If the worker is down for a day, the
web `/health` reports `worker_last_seen` and the existing alerts bot pings Pedro.

### 4.7 Dashboard

`/dashboard/workflow` gets a "Fila" panel: queued (position, ETA; strict FIFO), backlog of over-cap themes with "Gerar agora", running (phase, started, heartbeat),
retry_wait (next attempt), dead_letter (reason, Retry/Discard). API (reads `generation_runs`): `GET /api/generation-runs?status=…`,
`POST /api/generation-runs/{id}/retry`, `POST /api/generation-runs/{id}/cancel` (owner/admin only, CAS on status).
Interactive Start/Resume buttons return 202 with the job id and the existing SSE stream reports progress (the SSE hub
must move to Redis pub/sub or Postgres LISTEN/NOTIFY because the worker is a different process — see 4.8).

### 4.8 Cross-process concerns created by the split

- SSE progress: today an in-process hub. The worker publishes progress events through Postgres `NOTIFY
  carousel_progress, '<json>'` (or the existing Redis) and the web process relays them to SSE clients. Choose NOTIFY
  (no new dependency, payload < 8 kB, ids only + phase).
- SSE reconnect: NOTIFY is fire-and-forget, so every SSE (re)connect first sends the current state from the existing
  workflow-state query, then streams; a client that missed NOTIFYs during a web restart catches up at once.
- Queue observability (round-3 review): `/health` and the dashboard expose queue depth, oldest queued age, p50/p95 wait
  time, running job age and dead-letter count; the alerts bot pings Pedro when the oldest queued job waits > 6 h, a
  running job exceeds 2× the measured p95 phase time, or dead letters > 0 at the 04:00 summary.
- `worker_last_seen`: PgQueuer's per-worker heartbeat/statistics rows; `/health` reports the newest timestamp and the
  alerts bot pings Pedro when it is older than 10 min. The alert is always armed: the worker is live from the P1 merge.
- Step ownership (decided here, not in the ticket):

  | periodic step | owner |
  |---|---|
  | autopilot runner stepping, rework step, run recovery, stale-run reaper, drift reconciler, republish sweeper, daily scan, dispatcher | worker |
  | scheduled blog publish, reminders, Telegram notices (outbox cursor), Instagram publish claim, credential refresh, alerts | web (light, no LLM/Chromium) |
- Model breakers and the image-bridge semaphore are per process: they now live in the worker, which is the only
  process making generation calls — fine. The chat (web) keeps its own breaker registry.
- The reaper's in-memory counters move to the worker (single instance) or become a column-free query on
  `lease_until`.

## 6. Testing

- Unit: error classification table (transient vs permanent); jitter bounds; poison guard on our attempt counter;
  dedupe key construction; mapping of PgQueuer job events to `generation_runs` states.
- Integration (Postgres, PgQueuer installed by the same one-shot the deploy uses): FIFO dequeue; `concurrency_limit=1`
  holds with two worker processes; per-project advisory lock prevents two jobs on one carousel; a killed worker's job
  is re-queued after the heartbeat timeout and resumes from the checkpoint; a crash loop ends in `dead_letter` via our
  counter; Telegram double-tap → one run and one job; dead letter → Retry requeues once; the one-shot is idempotent
  (second run is a no-op).
- Gherkin features: "Several approved themes are generated one after another", "A run interrupted by a deploy resumes
  by itself", "A run that keeps failing is parked with its reason", "Pedro retries a parked run from Telegram", "The
  daily scan recovers a stuck run", "The website stays responsive while a carousel renders".
- Load/chaos validation (ADR-0026 §Validation) on a staging-like box before P1 merges (it is live on merge). There is no staging
  today: use a disposable DigitalOcean droplet of the same size (s-2vcpu-4gb, billed hourly, destroyed after the test)
  restored from a prod DATA backup, with the load generator on another machine (the laptop or the pi) so it does not
  contaminate p95.
- **Validation isolation (round-3 BLOCKER):** the test droplet must never reach production side effects. Its `.env` is
  built from a template, NOT copied from prod: every outbound credential (Telegram owner/alerts bots, Meta/Instagram,
  Pinecone, GrokBot webhook, OpenAI/LLM/image keys, SMTP) is replaced by a stub; `AUTOPILOT_ENABLED=false` for the web
  path, Instagram publish and Telegram notices disabled; LLM and image calls go to a local mock server that replays
  recorded responses with realistic latency (so phase timings are real but nothing is billed); the Grok bridge webhook
  points at the mock. A DigitalOcean cloud firewall allows egress only to package mirrors and the mock host. The build
  script has a test that fails if any prod credential value (compared by hash) is present on the droplet. Only
  `CAROUSEL_CHECKPOINT_BACKEND=postgres` and the DB/Redis settings come from the prod template.
- Never run mutation locally; CI mutation gate covers the new modules.

## 7. Rollout and rollback

- No feature flag (Pedro, 2026-10-23): P1 goes live when its PR merges, with `GENERATION_WORKER_CONCURRENCY=1`.
  The load test and the chaos steps (ADR-0026 §Validation) run on the disposable droplet against the PR branch
  BEFORE the merge, and the results are attached to the PR.
- Ownership uses ONE primitive on every path: the per-project drive lock (a session advisory lock on a dedicated
  connection) is taken by the worker's job handler and by any web path that still drives a phase (the synchronous
  dashboard start) for the whole time it drives; whoever does not get it does not drive. Skip rules are only an
  optimisation on top. Integration test: two drivers claim the same project concurrently → exactly one drives
  (deterministic race test).
- Deploys: the deploy runs `docker compose down` for the whole project (`.github/workflows/deploy.yml:234`), so the worker
  restarts on every deploy too. The guarantee is **auto-resume**, not survival: P1 adds a pre-`down` drain step (signal
  the worker to stop dequeuing; wait up to 5 min for the current phase to reach a checkpoint) and `down -t 120`, and the
  chaos test measures resume latency (target: resumed within 6 min of the stack coming back).
- Rollback: revert the P1 merge. Before the revert deploys, on the droplet with the current image:
  `docker compose -f docker-compose.prod.yml stop -t 300 generation-worker` (drains the current phase), then
  `docker compose -f docker-compose.prod.yml run --rm --no-deps backend python -m
  rag_backend.scripts.generation_queue_rollback --apply`: dashboard resumes the worker never started go back to
  their gate (their row is `in_progress` with no heartbeat, which the reverted reaper would never reap) and every
  active `generation_runs` row is cancelled. After the revert deploys, `docker compose -f docker-compose.prod.yml
  rm -sf generation-worker` removes the worker (the reverted compose file no longer names it, so `down` would leave
  it running). Autopilot runs are not stranded: their source of truth stays `autopilot_runs`, so the reverted
  in-process runner selects every `queued`/`generating`/`reworking` run again, and a phase the worker was driving
  when it stopped is parked by the reaper and re-driven by the runner's parked-workflow path. No schema rollback is
  needed (new tables only); `generation_runs` and PgQueuer's tables stay, unread. Removing PgQueuer entirely later
  = drop its tables in a one-shot.
  P1 must not change the meaning of the existing autopilot run statuses (a queued run that only existed as a
  `generation_runs` row would be stranded by a revert); the droplet validation rehearses one revert to prove none is.
- Deploy order: P0 → P5 → P1 validation on the droplet → P1 merge (live) → P2-P4.

## 8. Risks and open questions

- PgQueuer semantics gate (round-1/2 review): before P1 code is merged, a verification matrix against the PINNED
  version's source (not docs), each backed by an integration test that fails on mismatch: (a) dedupe_key lifecycle vs
  completed and held jobs (a "Tentar de novo" requeue with the same key must be accepted), (b) delayed enqueue, (c)
  configurable heartbeat_timeout, (d) attempt accounting on stale-heartbeat requeue, (e) FIFO under concurrency_limit, (f)
  held-job requeue API, (g) schedule dedupe across workers/restarts (the 04:00 scan runs once), (h) purge/retention API.
- Honest cost (round-2 review): because `generation_runs` is the source of truth and the daily scan self-heals a lossy
  queue, PgQueuer contributes the dequeue/heartbeat/requeue/schedule primitives; the in-house fallback is roughly the same
  surface minus those primitives. PgQueuer is chosen for operability (CLI, held jobs, schedules), not because it removes
  most of our code. Transactional enqueue is no longer needed (outbox dispatcher). If (a), (c) or (e) fails, switch to the
  in-house fallback behind the same entrypoints.
- Over-cap backlog (round-1 review): at most 10 themes; a theme older than 7 days expires with one Telegram note; Pedro can
  still trigger any backlog theme manually. Steady state at cap 3 and 1-3 topics/day is ~0; at cap 1 the 7-day expiry
  bounds it to ≤ 14.
- FIFO vs the per-project lock: with concurrency 1 the only conflict is an interactive edit (repair/republish/slide edit)
  holding the project lock; the handler waits up to 60 s for it, then re-enqueues with a 2 min delay — documented FIFO
  exception, shown as "aguardando edição" in the queue panel.
- Schema governance (round-2 review: one mechanism): the **authoritative** mechanism is the idempotent deploy one-shot
  (palette_timestamptz pattern) that runs before the stack starts: `CREATE TABLE IF NOT EXISTS generation_runs …`,
  the indexes, the `carousel_projects(phase_status, current_phase)` index and `pgq install/upgrade`. An Alembic migration
  file with identical DDL is kept only for fresh/dev databases and is checked against the ORM by the existing schema-drift
  CI gate; this plan does NOT re-enable migrate-on-deploy (the one-time `alembic stamp` reconcile in deploy.yml:255-262
  stays out of scope). The backend's `create_all` would create the same table if the one-shot had not run — identical
  DDL, so no drift; the worker never runs `create_all`. Fail-closed: if the one-shot fails, the dispatcher reports it and
  runs stay `queued`; approvals keep working. ADR-0026 records ADR-012 as amended.
- PgQueuer is a dependency we do not control: pin the version, read its changelog on upgrades, keep our own run table
  so the dashboard/Telegram never depend on PgQueuer's schema; if it is ever abandoned, the same entrypoints can run on
  an in-house `SKIP LOCKED` loop (the rejected option 1 of ADR-0026) without changing callers.
- At-least-once duplicates: any non-idempotent side effect inside a node (e.g. a Telegram send not via outbox) would
  repeat on lease expiry — audit nodes in P1 (list them in the ticket).
- Worker memory: Chromium HD export may exceed 1.4 GB on some carousels → measure in P0 and either raise the limit,
  drop HD from the autopilot path, or render HD on demand.
- Pedro's decisions (2026-10-22): concurrency 1; over-cap themes roll to the next day and can be triggered manually
  from the dashboard; recovery scan 04:00 BRT; strict FIFO (dashboard runs do not jump the queue; no priority column).
- Pedro's decision (2026-10-23): no feature flag for the queue. P1 goes live on merge after the disposable-droplet
  validation (load test, worker killed mid-phase, a full deploy mid-run, no duplicate artifacts or Telegram messages);
  rollback is a revert. This makes the flag semantics and hand-over findings of the skeptical review (rounds 1-3) moot;
  the single ownership lock stays.

## 9. Implementation notes (P1)

- Autopilot approvals need no extra outbox write: the autopilot run's own CAS into `queued`/`generating`/`reworking`
  is the durable record, and the dispatcher stages one `generation_runs` row per such run within 10 s. Dashboard
  resumes stage their row in the route's transaction (the review decision has no other durable record).
- One PgQueuer entrypoint carries every kind, so `concurrency_limit` is global and FIFO holds across kinds; one
  `autopilot_drive` job steps a run until it waits for the owner.
- The per-project drive lock has its own key space (the runner's autofix steps take the artifact-mutation lock from
  another session). A job that gets the lock and finds the project `in_progress` reaps it at once and re-drives the
  parked node; this replaces the 3-observation reaper wait and the 10-minute parked grace after a deploy or a crash.
- FIFO is strict at dequeue, with three gaps where a later job runs first, all bounded: (1) an autopilot run that
  waits for the owner is retried every 60 s with its job id, so it keeps its place but does not block the queue while it
  waits; (2) a job whose project drive lock is held (a synchronous dashboard start, an interactive edit) waits 60 s for
  it, then is retried after 2 min; (3) a transient failure retries after its backoff (30 s doubling, at most 30 min),
  and jobs behind it run meanwhile. Strict FIFO with the queue blocked on any of these would stall every theme behind
  one waiting owner or one slow provider.
- Cutover and later deploys: the deploy one-shot (`generation_queue_schema --apply`, stack down) queues a recovery
  (`adopt:<project>`) for each carousel project left `in_progress` with no active run and no autopilot run: the
  dashboard resume the old web process was running when the cutover deploy stopped it, or a synchronous dashboard
  start a later deploy killed. The worker reaps and re-drives it like a re-picked resume, never re-applying a decision;
  a project whose drive lock is held is skipped. Autopilot runs need nothing: the dispatcher stages them.
- Queue health: `/health/ready` reports depth, ages and dead letters; the worker names its long-lived connection
  `generation-worker`, so `pg_stat_activity` shows whether it is up; the web alerts Pedro after 10 min without it or
  when the oldest queued run waits over 6 h.
