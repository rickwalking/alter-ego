# Architecture Plan: AE-0517 — Carousel generation queue, dead letter and daily recovery

**Date:** 2026-10-22
**Status:** Plan (ADR-0026 proposed)
**Mode:** architect-skill plan mode
**Tier:** T3 (concurrency, failure recovery, new runtime component)

## 1. Goal

Pedro can approve several themes on the same day and they are generated one after another (bounded concurrency),
in order, without blocking each other, without slowing the website, and without getting lost on deploys or crashes.
Transient failures retry automatically; runs that keep failing land in a visible dead-letter state with the reason;
a daily scan recovers stuck work. No new paid service, no heavy infrastructure.

## 2. Findings that shape the design (evidence)

Current execution model (origin/main 23208e4f4):

- Topics arrive from the external Grok Bot at 08:00 BRT (`ops/grokbot/grok-bot/v3/routine.md`) via
  `POST /api/autopilot/topics` → `TopicIntakeService.accept` (`modules/autopilot/application/topic_intake.py:126`) →
  `autopilot_runs(state='queued')`. The daily cap is enforced only at intake; over-cap topics are stored and never
  queued (`domain/intake.py:254-266`).
- Pedro's Telegram approval per theme is the POV-thesis prompt (`application/thesis_prompts.py:74-110`): Confirmar
  moves `awaiting_thesis → queued` (CAS) but does not start anything. All prompts of the morning batch arrive together.
- The runner (`modules/autopilot/application/runner.py:162-232`) runs inside the 60 s in-process worker loop
  (`application/workers/workflow_workers.py:221-272`, started from the uvicorn lifespan, `bootstrap/app_factory.py:156`).
  `RUNS_PER_TICK=1` and `_first_run` (generating → reworking → queued) serialize autopilot runs by accident, and each
  phase is awaited inline, blocking reapers, publish and notices.
- Interactive resumes: `asyncio.create_task` in the web process, no global limit
  (`editorial_workflow_resume_runner.py:75,106-116`).
- Deploy = `docker compose down/up` (`.github/workflows/deploy.yml:230-234`), no grace period; lifespan shutdown does not
  drain carousel tasks; reaper (`infrastructure/database/carousel_run_reaper.py:89-224`) parks orphans for a human;
  no automatic re-run.
- LangGraph checkpointer: AsyncPostgresSaver in prod (deploy writes CHECKPOINTER=postgres), thread id = project id;
  re-driving replays only the interrupted node. Checkpoint pruning is broken (AE-0342, DB reached 1.4 GB).
- Prod applies schema with `Base.metadata.create_all` (new tables are created, new columns are not); alembic does not
  run on deploy.

Capacity (prod, 2026-10-22, read-only):

- 2 vCPU / 3.8 GB RAM, ~860 MB available, 2 GB swap ~35-47 % used, committed memory ~190 % all week; no OOM kills in
  30 days. backend, langfuse (762 MB), frontend, postgres have no memory limit; nothing has CPU shares.
- backend = one uvicorn process, one event loop. Heavy local steps: 4 headless Chromium launches per carousel
  (`infrastructure/external/playwright_export.py:308`, HD at deviceScaleFactor 2, 2800×3600), synchronous PIL
  re-saves (`_crop_border_artifact`) and img2pdf (`PdfSlideBuilder.build`) on the event loop.
- Daily batch: 3 runs created ~11:04-11:12 UTC; 10-21 and 10-22 each had one `escalated / run_stale` from that batch
  (cause unconfirmed).

Options research (sources in ADR-0026 discussion; summary): Postgres-native queues fit best (no new service,
transactional enqueue). PgQueuer is the strongest library; arq is maintenance-only; Celery has no native async;
LangGraph Agent Server needs a paid license. External free tiers (GitHub Actions cron, QStash, Cloudflare Queues) are
acceptable only as triggers, never as the queue (content must not leave the box).

## 3. ADR check

Required: yes. `docs/decisions/0026-carousel-generation-queue.md` (status proposed). Decision (Pedro, 2026-10-22):
**PgQueuer** (MIT, asyncpg-native Postgres queue) as the job engine, consumed by a separate resource-capped worker
container; our own `generation_runs` table stays the source of truth for the dashboard, Telegram and idempotency. The
AE-0017 recovery plan explicitly requires an ADR before any new queue mechanism.

## 4. Target design

### 4.1 Components

```
Grok Bot ──► /api/autopilot/topics ──► autopilot_runs(queued)
Telegram (Confirmar thesis / Aprovar) ──► CAS + generation_runs row + PgQueuer enqueue   ┐ web: backend (uvicorn)
Dashboard (Start / Resume / Retry)    ──► generation_runs row + PgQueuer enqueue (202)   ┘ never runs a graph phase
PgQueuer tables (Postgres) ◄── generation-worker (same image, cmd `pgq run rag_backend.worker.main:create_pgqueuer`)
                                 ├─ entrypoints: autopilot_start, autopilot_step, workflow_resume, workflow_start
                                 ├─ one LangGraph phase per job (resume from checkpoint), concurrency_limit=1
                                 ├─ PgQueuer retries (backoff), on_failure="hold" = dead letter, heartbeat requeue
                                 ├─ global export lock = 1 (Chromium)
                                 └─ @schedule("0 7 * * *") daily recovery scan (= 04:00 BRT) + light periodic steps
```

### 4.2 Data model

PgQueuer owns its own tables (`pgqueuer`, `pgqueuer_log`, `pgqueuer_statistics`, `pgqueuer_schedules`; exact names per
the pinned version). Prod does not run migrations, so they are installed by an idempotent **deploy one-shot**
(`pgq install` on first deploy, `pgq upgrade` afterwards — it applies only missing pieces) in deploy.yml right after the
blog cutover step, using the palette_timestamptz pattern: never blocks the stack, fails the job at the end on error. The
PgQueuer version is pinned in `backend/pyproject.toml` / `uv.lock`; upgrades are their own PR.

Our own table (new table → created by `create_all`, no ALTER) `generation_runs` — what Pedro sees and what Telegram
and the autopilot state machine reference:

| column | type | notes |
|---|---|---|
| id | uuid pk | also the LangGraph-independent run id |
| kind | varchar(32) | `autopilot_start`, `autopilot_step`, `workflow_resume`, `workflow_start` |
| carousel_project_id / autopilot_run_id | uuid null | FKs |
| dedupe_key | varchar(160) | partial UNIQUE where status in (queued, running, retry_wait); also passed to PgQueuer as `dedupe_key` |
| pgq_job_id | bigint null | current PgQueuer job id (changes on retry/requeue) |
| payload | jsonb | typed per kind (Pydantic) |
| status | varchar(16) | `queued`, `running`, `retry_wait`, `succeeded`, `dead_letter`, `cancelled` |
| attempts / max_attempts | smallint | **our own counter**, incremented at job start (poison guard, see 4.3); default max 4 |
| next_attempt_at | timestamptz null | shown in the dashboard while `retry_wait` |
| last_error_code / last_error | varchar / text | classified error (no secrets, truncated) |
| created_at / started_at / finished_at / updated_at | timestamptz | |

Indexes: `(status, created_at)`; partial unique `(dedupe_key)`; `(carousel_project_id)`; `(autopilot_run_id)`. Also the
missing index on `carousel_projects(phase_status, current_phase)` (index on an existing table → same deploy one-shot,
`CREATE INDEX CONCURRENTLY IF NOT EXISTS`).

### 4.3 Claim, lease, retry, dead letter (PgQueuer + our guards)

- Enqueue: in the same transaction as the CAS that triggered it (Telegram callback, resume route), insert the
  `generation_runs` row (`ON CONFLICT (dedupe_key) DO NOTHING`) and call PgQueuer's `enqueue(entrypoint, payload=run_id,
  dedupe_key=...)` on the same connection, so a double tap or a webhook retry yields one run and one job, and a rolled
  back CAS leaves neither.
- Claim and concurrency: PgQueuer dequeues with `FOR UPDATE SKIP LOCKED` in FIFO order (strict FIFO, Pedro's decision);
  `concurrency_limit=1` per entrypoint group, enforced in the database across workers (`GENERATION_WORKER_CONCURRENCY`,
  default 1). Per-project exclusivity: the job handler takes `pg_try_advisory_xact_lock(project)`; if another run holds
  it, the job is re-enqueued with a short delay (never two jobs driving one carousel).
- Heartbeat: PgQueuer heartbeats from the worker's event loop; set `heartbeat_timeout` to 300 s (not the 30 s default)
  and run CPU-heavy steps (`_crop_border_artifact`, `PdfSlideBuilder.build`, PIL validation) in `asyncio.to_thread` so
  heartbeats are never starved (a starved heartbeat makes PgQueuer re-queue a live job → duplicate run).
- Retries: PgQueuer's retry executor (`DatabaseRetryEntrypointExecutor`): `max_attempts` 4, `initial_delay` 30 s,
  `backoff_multiplier` 2, `max_delay` 30 min; jitter ±20 % added by our handler (PgQueuer's docs do not document jitter).
  Only transient errors are retried (reuse `StartStatus.PROVIDER_OUTAGE`, model-breaker errors, HTTP 429/5xx/timeouts);
  permanent errors (validation, content-gate escalation, missing project) raise a non-retryable error → dead letter now.
- Dead letter: `on_failure="hold"` keeps failed jobs in PgQueuer as `failed`; our handler mirrors the state into
  `generation_runs.status='dead_letter'` with the classified reason; the autopilot run goes to `escalated`/`failed`
  exactly as today (CAS + outbox), so Telegram notices keep working. Retry from Telegram/dashboard = PgQueuer `requeue`
  + our row back to `queued` with attempts reset (CAS on `dead_letter`).
- **Poison guard (our own counter)**: PgQueuer does not document whether a stale-heartbeat requeue counts as an attempt.
  The handler increments `generation_runs.attempts` first thing; if it exceeds `max_attempts` it marks `dead_letter` and
  returns without running the graph. This stops a crash/OOM loop regardless of PgQueuer's accounting.
- Worker death (OOM, deploy): PgQueuer re-queues the job after the heartbeat timeout; LangGraph resumes the interrupted
  node from the checkpoint; the existing `run_epoch` fence + heartbeat columns on `carousel_projects` keep stale writers
  out. External side effects stay keyed/CAS-guarded: image bridge jobs (token), Instagram publish (claim), Telegram
  notices (outbox cursor), export writes by artifact version.

### 4.4 The worker

- New module `rag_backend/worker/main.py` exposing `create_pgqueuer()` (same image; command
  `pgq run rag_backend.worker.main:create_pgqueuer`). It builds the DI container like the app factory but starts no HTTP
  server, registers the entrypoints (`autopilot_start`, `autopilot_step`, `workflow_resume`, `workflow_start`) and the
  daily schedule. `concurrency_limit` = `GENERATION_WORKER_CONCURRENCY` (Pedro: 1). Graceful shutdown: PgQueuer stops
  dequeuing on SIGTERM; the current phase gets `stop_grace_period` (120 s); an unfinished job is re-queued by heartbeat
  timeout and resumes from the checkpoint (our attempt counter treats it as an attempt only if it actually started).
- Move the heavy loop steps out of the web process: autopilot runner stepping, rework step, recovery and the daily
  scan run in the worker. The web lifespan keeps only light, fast periodic steps (scheduled blog publish, reminders,
  notices) or they move too — implementation detail decided in the ticket, with the rule: nothing that awaits an LLM or
  Chromium runs in the web process.
- Global export semaphore (cross-process): a Postgres advisory lock `pg_try_advisory_lock(EXPORT_LOCK_KEY)` around
  `export_slides`, plus run PT/EN and standard/HD exports sequentially; Chromium flags `--disable-dev-shm-usage`,
  `--renderer-process-limit=1`. Move `_crop_border_artifact` and `PdfSlideBuilder.build` to `asyncio.to_thread`.
- Container limits (docker-compose.prod.yml): `mem_limit: 1400m`, `memswap_limit: 1400m` (fail the worker, not the box),
  `cpus: 1.0`, `cpu_shares: 256` (web services keep the default 1024 so visitors win contention), `shm_size: 256m`,
  `stop_grace_period: 120s`, `restart: unless-stopped`. Add reservations/limits to backend/frontend (and cap langfuse)
  in a separate infra ticket, measured first.
- DB pool for the worker: 3 connections (+ overflow 2), so the web pool (5+10) is not starved.

### 4.5 Telegram and the "approve several themes" flow

- Each thesis prompt keeps its Confirmar/Editar/Descartar buttons; Confirmar now also enqueues
  `autopilot_start` (dedupe `run:<id>:start`) and edits the message to show **"Na fila: posição N de M — início
  estimado HH:MM"** (position from the queue order, estimate from the moving average of recent job durations).
- New button on the morning batch summary: **"Aprovar todas"** confirms every pending thesis of the batch in one tap
  (each with its own CAS + enqueue).
- Over-cap topics (Pedro's decision): instead of being dropped, they are stored as a backlog with a `not_before` date
  (next day's slot) and appear in the next morning's prompts. They are also listed in the dashboard queue panel, where
  Pedro can trigger any of them manually ("Gerar agora": enqueue now, outside the daily cap). The daily cap keeps its
  meaning (max automatic generations started per day).
- When a job reaches `dead_letter`, Pedro gets one Telegram message with the reason and buttons **"Tentar de novo"**
  (re-enqueue with attempts reset, CAS on dead_letter) and **"Descartar"** — this also fixes AE-0410 (escalated runs
  could not be resumed from Telegram) for queue-originated failures.

### 4.6 Daily recovery scan (04:00 BRT = PgQueuer `@schedule("0 7 * * *")` in UTC; PgQueuer's schedules table makes it
run once per day across workers)

1. Approved/queued autopilot runs with no active job → enqueue (`autopilot_start`/`autopilot_step`).
2. `carousel_projects` in `phase_status='in_progress'` whose heartbeat is older than the lease and no running job →
   enqueue `workflow_resume` (replaces "park and wait for a human" for autopilot runs; interactive runs stay parked
   and are listed for Pedro).
3. `dead_letter` runs (PgQueuer `failed`, held) younger than 7 days whose error was transient-class (e.g. provider outage that lasted hours) →
   re-enqueue once (`recovery_attempt` flag) — never loops.
4. Expire/purge: `succeeded` `generation_runs` and PgQueuer log rows older than 30 days deleted; checkpoint pruning for published/rejected projects
   (fixes AE-0342's never-matching prefix).
5. Summary to Pedro (Telegram, one message): recovered N, still dead M, queue length K.
Optional external trigger (free): none needed; the worker owns the schedule. If the worker is down for a day, the
web `/health` reports `worker_last_seen` and the existing alerts bot pings Pedro.

### 4.7 Dashboard

`/dashboard/workflow` gets a "Fila" panel: queued (position, ETA; strict FIFO), backlog of over-cap themes with "Gerar agora", running (phase, started, heartbeat),
retry_wait (next attempt), dead_letter (reason, Retry/Discard). API (reads `generation_runs`): `GET /api/generation-runs?status=…`,
`POST /api/generation-runs/{id}/retry`, `POST /api/generation-runs/{id}/cancel` (owner/admin only, CAS on status).
Interactive Start/Resume buttons return 202 with the job id and the existing SSE stream reports progress (the SSE hub
must move to Redis pub/sub or Postgres LISTEN/NOTIFY because the worker is a different process — see 4.8).

### 4.8 Cross-process concerns created by the split

- SSE progress: today an in-process hub. The worker publishes progress events through Postgres `NOTIFY
  carousel_progress, '<json>'` (or the existing Redis) and the web process relays them to SSE clients. Choose NOTIFY
  (no new dependency, payload < 8 kB, ids only + phase).
- Model breakers and the image-bridge semaphore are per process: they now live in the worker, which is the only
  process making generation calls — fine. The chat (web) keeps its own breaker registry.
- The reaper's in-memory counters move to the worker (single instance) or become a column-free query on
  `lease_until`.

## 6. Testing

- Unit: error classification table (transient vs permanent); jitter bounds; poison guard on our attempt counter;
  dedupe key construction; mapping of PgQueuer job events to `generation_runs` states.
- Integration (Postgres, PgQueuer installed by the same one-shot the deploy uses): FIFO dequeue; `concurrency_limit=1`
  holds with two worker processes; per-project advisory lock prevents two jobs on one carousel; a killed worker's job
  is re-queued after the heartbeat timeout and resumes from the checkpoint; a crash loop ends in `dead_letter` via our
  counter; Telegram double-tap → one run and one job; dead letter → Retry requeues once; the one-shot is idempotent
  (second run is a no-op).
- Gherkin features: "Several approved themes are generated one after another", "A run interrupted by a deploy resumes
  by itself", "A run that keeps failing is parked with its reason", "Pedro retries a parked run from Telegram", "The
  daily scan recovers a stuck run", "The website stays responsive while a carousel renders".
- Load/chaos validation (ADR-0026 §Validation) on a staging-like box before enabling P1 in prod.
- Never run mutation locally; CI mutation gate covers the new modules.

## 7. Rollout and rollback

- Feature flag `GENERATION_QUEUE_ENABLED` (default false). With the flag off, the current in-process path runs
  unchanged; the worker container starts but only runs the daily scan in dry-run mode (logs what it would do).
- Enable in prod after the load/chaos validation; first with `GENERATION_WORKER_CONCURRENCY=1`.
- Rollback: flag off (web resumes in-process execution); `generation_runs` rows and PgQueuer jobs stay in their tables
  (harmless) and queued autopilot runs are replayed by the in-process runner's existing `queued` selection; no schema
  rollback needed (new tables only). Removing PgQueuer entirely later = drop its tables in a one-shot.
- Deploy order: P0 → P1 (flag off) → validation → flag on → P2-P4.

## 8. Risks and open questions

- PgQueuer is a dependency we do not control: pin the version, read its changelog on upgrades, keep our own run table
  so the dashboard/Telegram never depend on PgQueuer's schema; if it is ever abandoned, the same entrypoints can run on
  an in-house `SKIP LOCKED` loop (the rejected option 1 of ADR-0026) without changing callers.
- At-least-once duplicates: any non-idempotent side effect inside a node (e.g. a Telegram send not via outbox) would
  repeat on lease expiry — audit nodes in P1 (list them in the ticket).
- Worker memory: Chromium HD export may exceed 1.4 GB on some carousels → measure in P0 and either raise the limit,
  drop HD from the autopilot path, or render HD on demand.
- Pedro's decisions (2026-10-22): concurrency 1; over-cap themes roll to the next day and can be triggered manually
  from the dashboard; recovery scan 04:00 BRT; strict FIFO (dashboard runs do not jump the queue; no priority column).
