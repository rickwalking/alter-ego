# AE-0618 — dev summary

## Change

The daily recovery scan has a new step, after the two revive steps and before the purge. For each stuck run that never
got the owner's Retry it stages one `content.autopilot.escalation_renotice` outbox event and the `scan_renotified`
ledger marker in one transaction. The worker's notifier reads the event as KIND_ESCALATED and sends it with the carousel
Retry keyboard. The count goes into Pedro's summary and the scan's done log. Decisions are in the
ticket.

No run state, carousel, lock version or `updated_at` changes. No migration, gate, limit or validator changed.

Per Pedro's decision (2026-11-04), the first scan after the deploy sends one notice to 3 runs: b5f5ff39, 66873e0d and
92bdb9d9. Runs parked by the queue, runs with no carousel and owner-cancelled runs are excluded, and a parked or failed
publish notice that offered Retry counts as a Retry notice. `stage()` repeats every check under the row lock, and the
carousel check takes a shared lock on the carousel row. This has not been run against production data.
