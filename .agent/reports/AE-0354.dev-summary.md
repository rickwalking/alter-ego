## What changed

- The workflow worker, after the Instagram publish step, calls an in-process autopilot runner when `autopilot_enabled` is true. The runner takes at most one run per tick and does not hold a lock across ticks.
- A queued run creates a private pt-BR carousel (`generate_images=true`, at most 10 slides) owned by `autopilot_owner_user_id`, starts the editorial workflow with no HTTP call, and moves to `generating`. The reviewer id stays unset.
- Gate policy is pure: research needs 3 findings with content; outline length must match the slide total; content needs a persona score of at least `VOICE_MATCH_MIN_SCORE` (70) and no forbidden phrase; design needs a presentation report with no blockers; every image must be a 1080×1350 JPEG. A failed check revises at most twice, then the run is `escalated`.
- `final_review` is never approved. The run becomes `awaiting_owner` and one `content.autopilot.ready_for_owner` outbox event is staged, only when the compare-and-set succeeds.
- A lock conflict or a provider outage on resume is left for the next tick. Three start outages (429/503) move `queued` to `failed` with reason `start_failed`.
- Langfuse metadata on start and resume is `content_type=carousel`, `agent_name=autopilot`, plus `phase` and `project_id`.

## Deviations

- `AutopilotRunner.tick()` takes no session. The worker collaborator is `AutopilotRunnerTickAdapter.tick(db)`. The application package cannot import SQLAlchemy.
- Design uses the same two-revise cap as the other gates (ticket acceptance criteria and architecture §6). Architecture §3 still says the presentation pass revises once.
- `queued` → `failed` was added to the domain table and to architecture §4 so a start outage can fail the run.
